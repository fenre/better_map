# CIM Network Traffic — H3 hexbin

The strategic-view complement to the
[cim-network-traffic/markers](./markers.md) and
[cim-network-traffic/paths](./paths.md) recipes — same
CIM-accelerated `Network_Traffic` data model, same `iplocation`
geocoding, but rolled into [H3](https://h3geo.org/) hexagonal cells
coloured by total byte volume. Answers the strategic question
**"where, geographically, is most of my egress / ingress
concentrated?"** at a glance, without the per-destination noise
that swamps a marker view at world zoom.

## 1. Source description

Same Splunk **Network Traffic** Common Information Model (CIM)
data model as the companion [markers](./markers.md) and
[paths](./paths.md) recipes — vendor-agnostic at the SPL layer
because the data model normalises Palo Alto, Cisco ASA / FTD,
Splunk Stream, NetFlow / sFlow / IPFIX, Meraki MX, Cisco
Secure Firewall, and any other source tagged
`network + communicate`.

**Why H3 hexbin for CIM Network Traffic.** A markers view of
500-5000 destination IPs starts to overlap in CDN-dense regions
(US-east, Frankfurt, Dublin, Tokyo, Singapore). Clustering
helps but loses the per-region byte-volume story. H3 hexbin
SUMS the per-destination bytes inside each hex cell — so a
heavy hex over Frankfurt tells you "20 % of your egress goes
to Frankfurt-region IPs" in one colour, regardless of how
many distinct destinations are inside that hex. This is the
right layer for **executive / SOC-leadership** views of
network traffic, not investigator views (use markers or paths
for those).

**Typical sourcetype / index:** anything tagged
`network communicate` (check
`| tstats values(sourcetype) WHERE \`cim_Network_Traffic_indexes\`
tag=network tag=communicate`); typical index is `network` or
the vendor-specific index (`pan_logs`, `cisco_secure_fw`,
`netflow`, etc.). This recipe queries the data-model
accelerated summary, so the source index does not appear in
the SPL — that is the whole point of CIM.

## 2. SPL recipe

```spl
| tstats summariesonly=true sum(All_Traffic.bytes) AS bytes, count AS event_count FROM datamodel=Network_Traffic WHERE All_Traffic.action="allowed" earliest=-24h latest=now BY All_Traffic.dest
| rename All_Traffic.dest AS dest
| where match(dest, "^\d+\.\d+\.\d+\.\d+$")
| iplocation dest
| where isnotnull(lat) AND isnotnull(lon)
| rename dest AS id, Country AS dest_country, bytes AS value
| fields id, lat, lon, value, dest_country, event_count
| sort - value
| head 5000
```

Why this exact shape, line by line:

- **`| tstats summariesonly=true sum(All_Traffic.bytes) AS bytes,
  count AS event_count FROM datamodel=Network_Traffic`** —
  reads the CIM-accelerated data model summary, NOT raw
  events. Two aggregates in a single pass: total bytes per
  destination (drives the hex colour ramp via `value`), and
  event count per destination (kept as a tooltip / drilldown
  field). `summariesonly=true` is the explicit promise "I
  want accelerated data only" — falls through cleanly to zero
  results (not raw scan) if acceleration is not enabled.
- **`WHERE All_Traffic.action="allowed"`** — data-model-layer
  filter. Change to `"blocked"` to flip the panel to a
  "where, geographically, is most of my denied traffic going?"
  SOC view, which is high-value for an executive briefing on
  perimeter posture.
- **`BY All_Traffic.dest`** — one row per unique destination
  IP. The hex binning happens client-side after `iplocation`
  resolves each `dest` to a lat / lon — the H3 layer then
  groups all destinations whose lat / lon fall inside a
  single hex cell.
- **`| where match(dest, "^\d+\.\d+\.\d+\.\d+$")`** — IPv4-only
  filter (same as the markers recipe). Drop or relax for
  IPv6-heavy environments.
- **`| iplocation dest`** — Splunk's built-in MaxMind
  GeoLite2 geocoder. No outbound network call. RFC-1918
  destinations get null lat / lon; the `where` filter on the
  next line drops them.
- **`| where isnotnull(lat) AND isnotnull(lon)`** — drops
  private-range IPs that would otherwise pile up at Null
  Island (0, 0).
- **`| rename dest AS id, Country AS dest_country, bytes AS
  value`** — adopt Better Map's auto-detected aliases. The
  H3 layer auto-picks `value` as the aggregation field, so
  no `hexbinValueField` override is needed in the formatter.
- **`| head 5000`** — render budget. The H3 hexbin layer
  collapses 5000 destinations into at most a few hundred
  visible hex cells at resolution 3, so the panel stays
  responsive even on busy perimeters.

## 4. Recommended formatter config

```json
{
  "pointRenderer": "h3",
  "hexbinAggregate": "sum",
  "hexbinResolution": 3,
  "hexbinOpacity": 0.7
}
```

Why this specific config:

- **`pointRenderer: "h3"`** — explicit pin to the H3 hexbin
  renderer. Without the pin, the `auto` renderer might fall
  back to markers below a row-count threshold and silently
  demote the panel from "strategic byte-volume map" to
  "individual destination map." Pinning makes the panel
  intent visible in the formatter config and stable across
  row-count fluctuations (off-hours dips, holiday weekends).
- **`hexbinAggregate: "sum"`** — sum the per-row `value`
  field (bytes) across all destinations in each hex cell.
  `sum` is correct for "total byte volume per region";
  `mean` is appropriate only if the dashboard question is
  "average bandwidth per session" (which it is not for an
  egress map). `count` ignores the byte field entirely and
  would produce a "destination-density-per-region" view —
  use a different recipe for that.
- **`hexbinResolution: 3`** — H3 resolution 3 gives ~12,392
  cells globally, ~7,800 km² per cell — continental-to-
  large-country scale. Right for an executive view. Resolution
  4 (~57k global cells, ~1,770 km² per cell) is right for
  country-level visibility; resolution 5 (~400k cells,
  ~252 km² per cell) for city level. The layer reference
  documents the full grid. For a "is there anything weird
  happening in a specific city?" panel, raise to 5.
- **`hexbinOpacity: 0.7`** — slightly transparent so the
  underlying basemap labels show through; helps the executive
  audience orient cells against country names without losing
  the colour signal. Drop to 0.5 if the basemap is dark and
  the palette is light; raise to 0.9 if cells are small and
  the user can't distinguish colour differences.

## 6. Gotchas

- **CIM data-model acceleration MUST be enabled** on the
  `Network_Traffic` data model for `summariesonly=true` to
  return anything. Confirm in Settings → Data models →
  Network Traffic → Acceleration. If accel is OFF, the
  dashboard panel returns ZERO results (the correct, fail-
  safe behaviour). If you cannot enable acceleration, change
  the recipe to `summariesonly=false` (much slower; not
  recommended for any panel that auto-refreshes).
- **`sum(All_Traffic.bytes)` vs `sum(All_Traffic.bytes_out)`.**
  The CIM Network Traffic data model carries both `bytes`
  (total octets in flow) and `bytes_out` (egress octets
  only) — vendor-dependent. For a "what is the egress
  concentration?" map, use `bytes_out`. For a "what is the
  total traffic concentration?" map (egress + ingress), use
  `bytes` (the recipe default). NEVER mix the two across
  data sources — a Palo Alto record's `bytes` is comparable
  to a Cisco ASA record's `bytes`, but a Palo Alto `bytes_out`
  has no equivalent in older Cisco records that only carry
  `bytes`. Pick one field semantic per panel.
- **MaxMind database licensing.** Splunk Enterprise ships
  with the free MaxMind GeoLite2 database. For higher
  accuracy / commercial use, swap in MaxMind GeoIP2 via the
  Splunk admin UI. The recipe is unchanged — `iplocation`
  reads whichever database is configured.
- **Hex resolution vs row count.** Resolution 3 with < 100
  destinations may produce visually sparse cells (lots of
  empty hexes). Resolution 5 with > 50000 destinations
  starts pushing browser memory (hundreds of thousands of
  hex cells, each with per-cell aggregate state). Rule of
  thumb: pick the lowest resolution that gives ≥ 10× as
  many destinations as you have visible hex cells — keeps
  the panel meaningful and fast.
- **Time range.** The recipe hard-codes `earliest=-24h
  latest=now` so it works in a panel without a dashboard
  time picker. Replace with `earliest=$earliest$
  latest=$latest$` once you wire the recipe into a dashboard
  with a time-range input. For executive briefings,
  `earliest=-7d` over a 7-day window is more common.
- **`Null Island` cluster.** Forgot the `where isnotnull(lat)
  AND isnotnull(lon)` filter? Every private IP renders at
  `(0, 0)` and produces a single ENORMOUS hex cell off the
  coast of Ghana. Add the filter; that one cell is your
  private RFC-1918 traffic.
- **PII / GDPR posture.** Per ROADMAP §1a (binding), Better
  Map NEVER sends event data outside `splunkd:8089`.
  `iplocation` runs server-side against the local MaxMind
  database — no outbound geocoding API call. The hex-cell
  aggregation is BROADER than per-marker rendering (one hex
  covers an entire region's destinations), so this layer is
  generally LOWER-risk for privacy-sensitive deployments
  than the markers layer.
- **No OT safety dependency.** This recipe is pure IT
  network traffic. If your `Network_Traffic` data model
  ALSO ingests passive DPI of an OT zone (Cisco Cyber
  Vision, Claroty), filter THOSE sourcetypes out of this
  panel (`NOT sourcetype IN ("cisco:cv:*", "claroty:*")`)
  and put them in a DEDICATED recipe with explicit OT-
  safety annotations per
  [`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
  Rule 6. Mixing IT and OT traffic in one hex cell makes
  the panel both noisier AND a Rule 6 violation.

## Verification status

`status: unverified` in the frontmatter — the SPL is
structurally sound, follows the documented Splunk CIM contract
plus the canonical `tstats + iplocation + hexbin` pattern, and
uses only shipping Splunk built-ins (`tstats`, `iplocation`,
`Splunk_SA_CIM`). It has not been dispatched against the
v1.7-prep lab tenant in this PR because non-interactive admin
auth is not present in the agent workspace. A maintainer with
REST auth to a CIM-accelerated tenant should:

1. Run the recipe SPL with `summariesonly=false` first to
   confirm the data model has data for the queried time range.
2. Re-run with `summariesonly=true` (the recipe shape) to
   confirm acceleration is alive and returns the same shape.
3. Render the panel at resolutions 2, 3, 4, 5 to confirm the
   panel degrades gracefully (Better Map's H3 layer should
   never show browser jank or per-cell errors). If it does,
   drop a reproduction case in the
   [hexbin layer source](https://github.com/fenre/better_map/blob/main/better_map/appserver/static/visualizations/better_map/src/lib/layers/hexbin.js)
   PR queue.
4. Update the frontmatter to `status: verified`, fill in
   `verified_against` (e.g. "Splunk Enterprise 10.0 with
   Splunk_SA_CIM 6.0.x against a Palo Alto + Cisco FTD CIM-
   accelerated install"), and submit a follow-up PR. The CI
   gate `scripts/check-recipe-schema.py` will accept the
   change without touching the schema.
