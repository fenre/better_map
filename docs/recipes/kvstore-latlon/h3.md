# KV Store (lat/lon collection) — H3 hexbin

The regional-aggregate complement to the
[kvstore-latlon/markers](./markers.md),
[kvstore-latlon/heat](./heat.md), and
[kvstore-latlon/supercluster](./supercluster.md) recipes — same
`site_locations` KV-Store collection, same events-index join on
`site_id` for activity weight, but rendered as a **hard-edged
hexagonal partition** (Uber's H3 spatial index) instead of a
continuous heat surface or discrete markers. Each hex cell
shows the SUM of `event_count` for every site whose
(`lat`, `lon`) falls inside the hex. Completes the
`kvstore-latlon` source-row triplet (markers / heat /
supercluster / h3 — every kvstore-latlon layer now ships).

## 1. Source description

Same `site_locations` KV-Store collection as the
[markers](./markers.md), [heat](./heat.md), and
[supercluster](./supercluster.md) siblings — an inventory of
fixed sites with `site_id`, `site_name`, `lat`, `lon`,
`site_type` columns. The events join is the same shape as the
[heat sibling](./heat.md): an events index that carries a
`site_id` field (extracted via CIM `FIELDALIAS`, forwarder
`_meta`, or search-time `eval`), aggregated to
`stats count BY site_id`, then joined to the KV-Store for
coordinates.

The DIFFERENCE between the heat sibling and this h3 recipe is
the spatial-aggregation regime:

- **Heat layer** smooths sites into Gaussian blobs that BLEND
  across hex / region / city boundaries. Good for "where IS the
  pressure" continuous-gradient views, bad for "which JURISDICTION
  has the most pressure" boundary-aware views.
- **H3 layer** (this recipe) partitions the world into
  pre-computed hexagonal cells at a fixed resolution (here
  resolution 3 — continental-scale hexes ~190 km across) and
  SUMS the `event_count` of every site whose coordinates fall
  inside each hex. Each hex shows up as a discrete coloured
  polygon with a hard edge.

This makes the h3 layer right for:

- **Regional capacity briefings.** "Region 8b1 in continental
  Europe drew 1.2M events; region 822 in eastern North America
  drew 4.7M; region 8c4 in southeast Asia drew 89k." The hex
  partition gives boundary-aware totals that are easy to
  compare across continents.
- **Board-level deployment-scope maps.** "We deploy in 12
  H3-resolution-3 cells globally." The hard partition makes
  the scope count concrete.
- **Data-residency audits.** "Every active site in our fleet
  lives in a hex whose lat/lon falls within the contracted
  region." The hard partition surfaces residency violations as
  hexes appearing OUTSIDE the contracted region with non-zero
  `value`.

**H3 hexbin vs heat vs markers vs supercluster — which to
choose.**
- Use **markers** when the panel question is "which SITE is
  this?" (per-site identity, click for popup). Layer:
  [markers](./markers.md).
- Use **supercluster** when the panel question is "how many
  sites do I have per region, with cluster-expand drilldown"
  (200-250k sites, identity preserved via cluster expand-on-
  click). Layer: [supercluster](./supercluster.md).
- Use **heat** when the panel question is "where is the
  activity SMOOTHLY DISTRIBUTED?" (continuous gradient, no
  hard borders). Layer: [heat](./heat.md).
- Use **H3 hexbin** (this recipe) when the panel question is
  "which REGION (hard-bordered) has the most activity?"
  (boundary-aware totals, sortable, drillable, auditable). The
  hex resolution is the operator's control over what "region"
  means — see §4 for resolution selection.

**Typical sourcetype / index:** events index varies by use
case (`web`, `firewall`, `wineventlog`, `aws:cloudtrail`, ...);
the `site_locations` KV-Store is the same regardless. This
recipe assumes the `site_locations` collection already exists —
its one-time setup is documented in
[kvstore-latlon/markers](./markers.md#1-source-description) and
not duplicated here.

## 2. SPL recipe

```spl
index=web sourcetype=access_combined earliest=-1h latest=now
| stats count AS event_count BY site_id
| lookup site_locations site_id OUTPUT site_name, lat, lon, site_type
| where isnotnull(lat) AND isnotnull(lon)
| eval value=event_count
| rename site_id AS id
| fields id, lat, lon, site_name, site_type, event_count, value
| sort - event_count
| head 5000
```

Why this exact shape, line by line:

- **`index=web sourcetype=access_combined earliest=-1h latest=now`**
  — same events index pattern as the
  [heat sibling](./heat.md#2-spl-recipe). Change to whatever
  events index represents "activity" in your install. A 1 h
  window is the typical operations-dashboard slice; widen to
  24 h for executive briefings, narrow to 5 min for live ops.
- **`stats count AS event_count BY site_id`** — one row per
  site, with the count of events on that site in the window.
  This is the per-site activity total that becomes the
  per-hex aggregate after the hex layer's spatial bucketing.
- **`lookup site_locations site_id OUTPUT site_name, lat, lon,
  site_type`** — pull coordinates AND display fields from the
  KV Store. `site_id` is the join key on both sides (no `AS`
  alias needed — same name).
- **`where isnotnull(lat) AND isnotnull(lon)`** — drop any
  `site_id` value that is in the events stream but missing
  from `site_locations` (unregistered site, typo in the
  hostname enrichment, decommissioned site). The h3 layer
  REQUIRES coordinates on every row — un-coordinated rows
  would be silently dropped by the hexbin algorithm anyway,
  but explicit `where` makes the data-quality signal
  surface-able in a companion table panel.
- **`eval value=event_count`** — the h3 layer reads the
  `value` field by name (per Better Map's `dataFitness.js`
  field aliasing) for hexbin aggregation. Keeping a separate
  alias rather than renaming `event_count` directly preserves
  `event_count` for the per-feature popup ("this hex contains
  N events across M sites").
- **`rename site_id AS id`** — adopt Better Map's canonical
  `id` alias, same convention as every other recipe in the
  matrix. The `id` field is the per-site primary key, NOT
  the per-hex key (the hex layer computes its own per-cell
  key from the hexbin resolution + lat/lon bucket — see §4).
- **`fields id, lat, lon, site_name, site_type, event_count,
  value`** — explicit projection. Drops any transient columns
  the lookup brought in beyond the documented contract.
- **`sort - event_count`, `head 5000`** — render budget.
  The h3 hexbin aggregator buckets BEFORE rendering, so the
  per-cell cardinality is bounded by the H3 resolution
  (resolution 3 ≈ 41,162 cells globally, of which a typical
  fleet hits 1-200); the 5000-row pre-aggregation cap is on
  the per-SITE rows feeding the aggregator. 5000 covers a
  fleet of thousands of sites comfortably.

## 3. Expected fields

| field       | type   | example             |
|-------------|--------|---------------------|
| id          | string | DC-ATL-01           |
| lat         | number | 33.7490             |
| lon         | number | -84.3880            |
| site_name   | string | Atlanta data center |
| event_count | number | 1284                |
| value       | number | 1284                |

All six fields appear in `expected_fields` in the frontmatter
and are cross-checked by `scripts/check-recipe-schema.py`.
`site_type` flows through as a feature property for the per-
hex popup but is not strictly required by the h3 layer (the
h3 renderer reads only `lat`, `lon`, and `value`; the
descriptive columns survive the hex aggregation and appear in
the per-hex popup as a list of contained-site properties).

## 4. Recommended formatter config

```json
{
  "pointRenderer": "h3",
  "hexbinAggregate": "sum",
  "hexbinResolution": 3,
  "hexbinOpacity": 0.7
}
```

Why this specific config:

- **`pointRenderer: "h3"`** — explicit pin to the H3 hexbin
  renderer. The `auto` renderer would pick markers (≤ 200
  features), then cluster (200-10000), then heat (≥ 10000) —
  H3 is NEVER selected by `auto` because the spatial-
  aggregation regime is the operator's design choice, not a
  feature-count heuristic. Always pin explicitly when h3 is
  the intended layer.
- **`hexbinAggregate: "sum"`** — sum the `value` field across
  every site in each hex. The alternatives are `count` (count
  the SITES per hex, ignoring `value` — useful for "where do
  we have deployment density?" but not for "where is the
  activity volume concentrated?") and `avg` / `median` /
  `max` / `min` (useful for "what's the per-site MEAN
  activity?" but inverts the volume signal). For "regional
  activity volume" the right aggregate is `sum`. This
  matches the [cim-performance/h3](../cim-performance/h3.md)
  recipe (which sums `load_pressure`) and the
  [ot-datastreamer/h3](../ot-datastreamer/h3.md) recipe
  (which sums `event_count` per regional OT hub).
- **`hexbinResolution: 3`** — H3 resolution 3 gives hexes
  ~190 km across — continental scale, right for the global-
  fleet view (every cloud region in the world becomes one
  hex; major datacenter clusters each get their own hex). For
  per-country / per-state views, bump to resolution 4-5
  (~60-25 km). For per-city views, resolution 6-7 (~10-4
  km). For per-building views, resolution 8-9 (~1.5-0.6 km).
  See [Uber's H3 resolution
  reference](https://h3geo.org/docs/core-library/restable/)
  for the full table — every increment of `+1` divides the
  cell area by 7×.
- **`hexbinOpacity: 0.7`** — matches the
  [cim-performance/h3](../cim-performance/h3.md) recipe.
  At 1.0 the hexes fully occlude the basemap labels making
  the city / region names unreadable; at 0.5 the hexes are
  washed out and the colour ramp loses precision; 0.7 is the
  sweet spot for an executive / SRE audience that needs both
  the per-hex colour ramp AND the underlying geography
  context.
- **`value` drives hex colour intensity automatically.** The
  h3 layer renderer auto-picks the `value` field by name (per
  Better Map's `dataFitness.js` field aliasing). If you
  rename `value` in the SPL, also set the formatter's
  `hexbinValueField` option (or whichever name the formatter
  schema uses — check
  [`docs/_machine/formatter-schema.json`](https://github.com/fenre/better_map/blob/main/docs/_machine/formatter-schema.json)).

## 6. Gotchas

- **`site_id` extraction must already exist on the events.**
  Same gotcha as the
  [heat sibling §6](./heat.md#6-gotchas). If your events
  stream does not carry a `site_id` field, three common
  enrichment patterns: (1) `EVAL-site_id = case(match(host,
  "atl"), "DC-ATL-01", match(host, "fra"), "DC-FRA-01", ...)`
  in props.conf; (2) a separate `host_to_site.csv` lookup at
  index time (`LOOKUP-site = host_to_site host OUTPUTNEW
  site_id`); (3) a `_meta` annotation in `inputs.conf` on
  each forwarder (`_meta = site_id::DC-ATL-01`). Best
  practice is option 1 if your hostnames are regular; option
  2 if the mapping is irregular but stable; option 3 if you
  control the forwarders and want zero search-time cost.
- **`hexbinResolution` choice is the OPERATOR's call.** The
  default in the formatter config above is `3` (continental
  scale) which is right for a global-fleet view. For
  smaller-scope views you MUST adjust — a single-country
  panel at resolution 3 will show ONE hex covering the
  entire country, defeating the visualisation purpose. For
  per-country panels use resolution 4-5; for per-city use
  6-7; for per-building use 8-9. Splunk-side, the SPL is
  unchanged — the resolution choice is purely a formatter
  config.
- **H3 vs heat — when to choose which.** Two density-ish
  visualisations, two answers:

  | Layer | Shape | Best for |
  |---|---|---|
  | `heat` ([kvstore-latlon/heat](./heat.md)) | Continuous Gaussian blobs | "Where is the pressure" smooth-gradient views, executive briefings where the WHERE is more important than the BOUNDARY |
  | `h3` (this recipe) | Hard hex polygons at fixed resolution | "Which BOUNDED region has the most pressure" boundary-aware views, regional comparison rankings, data-residency audits |

  Both can coexist in the same dashboard with the same
  KV-Store collection — heat goes underneath (continuous
  base), h3 goes on top (hard-bordered overlay), and the
  operator gets both the smooth pressure surface AND the
  boundary-bounded totals. Toggle each layer independently
  via Better Map's BM-CT-1 layer contract (`setEnabled` /
  `isEnabled` / `reset`).
- **`sum` vs `count` vs `avg` aggregate choice.** The h3
  layer's `hexbinAggregate` option drives what each hex shows:
  - `sum`: total activity per hex (the recommended default
    for "regional volume" views).
  - `count`: number of features per hex (good for "where do
    we have site density?" but ignores `value`).
  - `avg` / `median`: per-site mean / median activity per
    hex (good for "what's the per-site mean activity?" but
    inverts the volume signal — a hex with 1 very-busy site
    and 100 quiet sites looks the same as a hex with 1 quiet
    site only).
  - `max` / `min`: extreme per-hex value (good for outlier
    detection, hot-site detection — "show me the hex that
    contains the busiest site").

  For typical "regional volume" panels stay on `sum`. For
  cluster-density panels switch to `count` and drop the
  `eval value=event_count` step (the count aggregate ignores
  `value`).
- **`value` field aliasing.** The h3 layer reads `value` by
  name. The recipe's `eval value=event_count` is what bridges
  the SPL's natural field name (`event_count`) to the
  formatter's expected field name (`value`). If you rename
  `value` in the SPL (e.g. `eval load_score=event_count *
  weight`), set the formatter's `hexbinValueField` option
  accordingly — the formatter does not auto-detect arbitrary
  rename targets, only the canonical names from
  `dataFitness.js` aliases.
- **Per-hex popup shows aggregated values.** The popup that
  appears when an operator hovers / clicks a hex shows the
  AGGREGATED `value` for that hex (the `sum`), NOT a list of
  the individual sites inside it. For per-site identity use
  the [markers sibling](./markers.md) — the two layers
  combine well: hex overlay for regional totals, markers
  underneath for per-site drilldown.
- **Empty result handling.** If the events index has zero
  matching events in the window, `stats count BY site_id`
  returns empty, the `lookup` returns nothing, the panel
  renders an empty h3 layer (no hex cells, no error). This
  is the correct behaviour — the h3 layer shouldn't pretend
  there is activity when there isn't. To distinguish "no
  events" from "events but no registered sites," add a
  companion single-value panel showing
  `| inputlookup site_locations | stats count`.
- **`max_event_count` cardinality — N/A for h3.** Unlike
  the [heat sibling](./heat.md), the h3 recipe does NOT
  normalise `value` to a `[0, 1]` band. The h3 layer's
  colour ramp auto-scales to the per-panel min/max of the
  `value` field. This is right for the h3 use case
  (regional comparison is intrinsically relative — "this
  hex is darker than that hex"), wrong for cross-panel
  comparison (two h3 panels for two different time windows
  would have independent colour ramps). For cross-panel
  comparison, set an explicit `hexbinValueMax` in the
  formatter config (check
  [`docs/_machine/formatter-schema.json`](https://github.com/fenre/better_map/blob/main/docs/_machine/formatter-schema.json)
  for the exact option name).
- **Time range.** The 1 h window in the recipe is a typical
  "operations dashboard" window. Widen to 24 h for
  executive briefings, narrow to 5 min for live ops. The
  KV-Store lookup itself is time-independent so the time
  range affects only the events `stats`.
- **No OT safety dependency.** As with the markers / heat /
  supercluster siblings, this is a pure IT / inventory
  layer. If `site_locations` contains SIS-related sites
  (Level-0/1/2 in the Purdue model — control rooms, RTU
  enclosures, SCADA workstations), follow
  [`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
  Rules 1 + 5 — split SIS sites into a separate dedicated
  h3 layer with `ot_safety_relevant: true` and a hand-
  curated tooltip that says "READ ONLY — this hex contains
  SIS-related assets; no action permitted from this panel."
  H3 aggregation does NOT distinguish per-site safety
  flags (the hex sum is a sum), so if you NEED per-hex
  safety surfaceability, pre-filter the SPL to one
  population at a time.

## Verification status

`status: unverified` in the frontmatter — the SPL is
structurally sound, follows the documented KV-Store + lookup
+ canonical h3 sum-aggregate pattern, mirrors the verified-
pattern shape of the
[cim-performance/h3](../cim-performance/h3.md) and
[ot-datastreamer/h3](../ot-datastreamer/h3.md) recipes, and
only references Splunk built-ins. It has not been dispatched
against a real `site_locations` collection joined to a real
events index in the v1.7-prep development cycle (the lab
tenant carries neither). A maintainer with REST auth to a
tenant with both a populated `site_locations` collection AND
a `site_id`-tagged events index (any sourcetype) should:

1. Confirm the events carry `site_id`:
   `index=<your_index> earliest=-1h | stats dc(site_id)`.
2. Confirm the join is non-empty:
   `index=<your_index> earliest=-1h
   | stats count BY site_id
   | lookup site_locations site_id OUTPUT lat
   | where isnotnull(lat)
   | stats count`.
3. Run the recipe SPL with `hexbinResolution: 3` and confirm
   the panel renders one hex per major geographic region.
   Vary `hexbinResolution` to 4-5 and confirm the cell count
   grows (one hex per country / state).
4. Update the frontmatter to `status: verified`, fill in
   `verified_against` with the events index / sourcetype
   pair, and submit a follow-up PR.
