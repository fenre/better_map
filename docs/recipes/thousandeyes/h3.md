# Cisco ThousandEyes (agent fleet) — H3 hexbin

The geographic-aggregation complement to the
[thousandeyes/markers](./markers.md) and
[thousandeyes/paths](./paths.md) recipes — same
`thousandeyes_agents` inventory + `thousandeyes_tests`
test-load join, but rendered as H3 hexagonal cells rather
than per-agent markers. The H3 layer surfaces **per-
region DEM AGENT FOOTPRINT** as hex cell colour intensity:
hot hexes indicate continental jurisdictions / metro
regions with the densest agent coverage AND the highest
aggregate test load; cool hexes indicate sparse coverage.
This is the natural shape for a **DEM capacity-planning
board view** (the question is "which geographic region
has dense / sparse agent coverage?" rather than "which
individual agent is overloaded" — use markers for that,
or "what path does each measurement traverse" — use
paths for that).

## 1. Source description

Same **Cisco ThousandEyes** sources as the markers
companion — see [thousandeyes/markers §1](./markers.md#1-source-description)
for the agent / test data model background. The relevant
distinction for THIS recipe: instead of one marker per
agent (which collapses to overlapping circles at world
zoom on a heavy-cloud-agent deployment), the recipe
aggregates agents AND their test-load BY (`lat`, `lon`)
site and renders the per-site agent footprint as H3
hexagonal cells.

**Why H3 hexbin for ThousandEyes.** A markers view at
world zoom collapses dense per-cloud-region agent
clusters (10-50 agents in `us-east-1`, `us-west-2`,
`eu-west-1`, etc.) into overlapping circles even with
the markers companion's `cluster` renderer. A heat view
(not yet shipped for thousandeyes) would solve the
density problem with a smooth Gaussian gradient, but
the heat blobs have NO hard borders — DEM capacity
planning that needs "how many agents in the APAC
jurisdiction?" cannot answer that from a Gaussian
gradient. An H3 hexbin AGGREGATES the underlying agents
into regular hexagonal cells (Uber's open H3 grid
system) and lets the viewer count "how many agents
live in THIS hex." The continental-scale resolution-3
cells map roughly to "North America" / "Western
Europe" / "APAC" — exactly the granularity a DEM
strategy review uses to plan agent footprint expansion.

**Typical sourcetype / index:** same as markers —
`index=thousandeyes_agents sourcetype="cisco:thousandeyes:agents"`
for the inventory, `index=thousandeyes_tests
sourcetype="cisco:thousandeyes:tests"` for the test
load join. App required: `ta_cisco_thousandeyes`
(Splunkbase id 7719). The H3 cell id is computed by
Better Map's h3 layer renderer at render time from the
`lat` / `lon` columns; the SPL does NOT pre-compute H3
cells (resolution-tuning stays in the formatter so an
operator can switch from continental resolution 3 to
metro resolution 7 mid-investigation without re-running
SPL).

## 2. SPL recipe

```spl
index=thousandeyes_agents sourcetype="cisco:thousandeyes:agents" earliest=-24h latest=now
| dedup agent_id sortby - _time
| where is_online="true"
| where isnotnull(agent_lat) AND isnotnull(agent_lon)
| join type=left agent_id [
    search index=thousandeyes_tests sourcetype="cisco:thousandeyes:tests" earliest=-24h latest=now
    | stats dc(test_id) AS test_count BY agent_id
  ]
| fillnull value=0 test_count
| stats count AS agent_count, sum(test_count) AS test_count BY agent_lat, agent_lon
| rename agent_lat AS lat, agent_lon AS lon
| eval value=test_count
| eval id=lat . "_" . lon
| fields id, lat, lon, value, agent_count, test_count
| sort - value
| head 5000
```

Why this exact shape, line by line:

- **`index=thousandeyes_agents sourcetype="cisco:thousandeyes:agents" earliest=-24h latest=now`** —
  same agent-inventory base search as the
  [markers companion §2](./markers.md#2-spl-recipe).
  The TA polls hourly by default; 24h guarantees
  every active agent appears at least once even if
  individual polls drop briefly.
- **`dedup agent_id sortby - _time`** — one row per
  agent (the freshest record). Inventory polls
  produce identical re-publishes when nothing
  changes; dedup picks the most recent state.
- **`where is_online="true"`** — drop offline /
  retired agents. **CRITICAL** — without this filter
  decommissioned agents at last-known coordinates
  inflate the cell-level agent count (a hex showing
  "47 agents" might actually have 30 live + 17
  offline, misleading the capacity-planning audience).
- **`where isnotnull(agent_lat) AND isnotnull(agent_lon)`** —
  drop agents without registered location. An
  unmapped agent surfaces in the companion paths
  recipe via the `agent_ip` fallback geocoding, but
  in THIS recipe (which is about per-region agent
  footprint) an agent with no anchor coordinate is
  by definition uncovered. Surface in a companion
  table panel for the DEM team to backfill.
- **`join` subsearch (tests-per-agent)** — count
  distinct active tests per agent (same shape as the
  markers companion's join). Bounded to the same 24h
  window. `dc(test_id)` excludes test re-runs (an
  agent running test X every 5 min for 24h is ONE
  test, not 288). The result feeds the cell-level
  `sum(test_count)` aggregation below.
- **`fillnull value=0 test_count`** — agents with no
  active tests (newly deployed, idle) get NULL from
  the join; promote to 0 so the per-cell sum doesn't
  short-circuit.
- **`stats count AS agent_count, sum(test_count) AS test_count BY agent_lat, agent_lon`** —
  THE pivotal line. Switch from per-agent to per-site
  aggregation. `count` counts how many agents are
  anchored at this (`agent_lat`, `agent_lon`)
  coordinate pair; `sum(test_count)` sums the test
  load across all agents at the site. One row per
  geographic site; the H3 renderer then aggregates
  THESE rows into hex cells based on
  `hexbinResolution`.
- **`rename agent_lat AS lat, agent_lon AS lon`** —
  adopt Better Map's canonical aliases (the markers
  companion does this earlier, before the join; the
  h3 recipe defers until after aggregation so the
  `BY` clause uses the source-of-truth field names).
- **`eval value=test_count`** — adopt Better Map's
  `value` alias for the h3-layer aggregate field. The
  default `hexbinAggregate` is `sum`, so the h3
  renderer computes `cell_value = sum(value)` per
  hex — the cell-level total test load across all
  agents in this jurisdiction. To render the cell-
  level agent count instead, swap to
  `eval value=agent_count` (cell aggregate becomes
  "total agents in this hex"). To render cell-level
  tests-per-agent average, swap to
  `eval value=round(test_count/agent_count, 1)` AND
  set `hexbinAggregate=avg`.
- **`eval id=lat . "_" . lon`** — h3 layer doesn't
  strictly need `id` (per-feature identity is moot
  for a cell aggregate), but the formatter `idField`
  enables the per-site hover popup at high zoom
  (Better Map's h3 renderer reverts to per-feature
  markers at building-resolution zoom levels). The
  `lat_lon` concatenation is stable because two
  sites cannot share both lat AND lon.
- **`fields ...`** — explicit projection. Drops
  `agent_id`, `agent_name`, `agent_type`, `country`,
  `network`, `os`, `version` (all per-agent fields
  that don't survive the per-site aggregation; for
  per-agent identity, use the markers companion).
  `agent_count` and `test_count` are carried so the
  per-site popup (at high zoom) can show "site
  Northern Virginia: 12 agents running 47 tests"
  alongside the cell aggregate.
- **`sort - value`** — most-loaded sites first
  (matters for the companion "Top 10 sites by test
  load" table panel; the h3 renderer itself is
  row-order-agnostic because it re-aggregates by
  hex).
- **`head 5000`** — render budget. Largest
  enterprise ThousandEyes deployments run 1000-2000
  agents across 50-100 distinct sites; 5000 is the
  safe upper bound on per-site rows.

Every `|` starts its own physical line per the SPL
pipe-per-line contract in `splunk-conf-and-spl.mdc`.

All six fields appear in `expected_fields` in the
frontmatter and are cross-checked by
`scripts/check-recipe-schema.py`. `value` is the h3-
layer-required aggregation field (drives
`hexbinAggregate`); `agent_count` and `test_count` are
carried for the per-site popup at high zoom (where the
h3 renderer reverts to per-feature markers). The `id`
shown in the example column is illustrative — the
actual SPL derives `id = lat . "_" . lon`; the H3 cell
id itself (`8a283082a677fff`-style) is computed at
render time by the h3 layer based on the formatter's
`hexbinResolution`.

## 4. Recommended formatter config

```json
{
  "pointRenderer": "h3",
  "hexbinAggregate": "sum",
  "hexbinResolution": 3,
  "hexbinOpacity": 0.7
}
```

Why this specific config:

- **`pointRenderer: "h3"`** — explicit pin to the h3
  renderer. The per-site aggregation in §2 often
  returns 50-100 cloud-region rows; without the
  explicit pin the renderer could stay on markers /
  cluster and miss the jurisdictional aggregation
  this panel is designed for.
- **`hexbinAggregate: "sum"`** — the default cell
  aggregate. `sum(value)` per hex cell gives the
  total DEM test load across all agents in this
  jurisdiction ("Western Europe: 247 tests across
  all monitored agents in this hex"). For the
  cell-level agent count variant (see §2 commentary),
  swap `eval value=agent_count` in SPL and keep
  `sum`. For the cell-level tests-per-agent
  variant, swap to `"avg"` so the cell value is the
  mean per-site ratio rather than a sum.
- **`hexbinResolution: 3`** — continental resolution.
  Resolution 3 cells span ~1500km² and map roughly
  to "North America" / "Western Europe" / "APAC" —
  ideal for the DEM strategy "which continental
  jurisdiction has dense / sparse agent coverage?"
  question this panel answers. Resolutions 4-5
  (~200km² / ~30km²) are right for country-level
  capacity reviews; resolutions 6-7 (~5km² / ~1km²)
  for metro / city views. A DEM strategy panel stays
  at 3; a country-team panel might go to 5; a city-
  level cloud-region panel to 7.
- **`hexbinOpacity: 0.7`** — matches the
  [es-risk/h3](../es-risk/h3.md),
  [kvstore-latlon/h3](../kvstore-latlon/h3.md), and
  [itsi-kpi-base/h3](../itsi-kpi-base/h3.md)
  recipes. At 1.0 the hex fully occludes city labels
  and country borders underneath; at 0.5 the cells
  are washed out; 0.7 is the sweet spot for the DEM
  / NetOps audience that needs to read BOTH the hex
  aggregate value AND the country / region context
  underneath.
- **`value` drives the hex aggregate automatically.**
  The h3 renderer auto-picks the `value` field by
  name (per Better Map's `dataFitness.js` field
  aliasing). If you rename `value` in the SPL, also
  set the formatter's `hexbinValueField` option —
  check
  [`docs/_machine/formatter-schema.json`](https://github.com/fenre/better_map/blob/main/docs/_machine/formatter-schema.json)
  for the exact property name.

## 6. Gotchas

- **The `is_online="true"` filter is non-negotiable.**
  Without it, decommissioned agents at last-known
  coordinates inflate the cell-level agent count.
  A hex showing "47 agents" might actually have 30
  live + 17 offline, misleading the capacity-
  planning audience. This is the same critical
  filter as the markers companion (see [markers §6
  Gotchas](./markers.md#6-gotchas)).
- **The test-load join is `_time`-window-bounded.**
  An agent that ran 12 tests yesterday but is idle
  for the last 24h gets `test_count=0` from the
  join → contributes 0 to the per-site
  `sum(test_count)`. This is INTENTIONAL — the
  panel renders CURRENT load, not historical load.
  For a "lifetime test load per agent" panel, swap
  the join's `earliest=-24h` to a longer window
  (e.g. `earliest=-30d`) at the cost of search
  performance.
- **H3 cells aggregate ACROSS cloud regions in the
  same continent.** Resolution 3 (~1500km²) puts
  AWS `us-east-1` (Northern Virginia) + `us-east-2`
  (Ohio) in the same hex; AWS `us-west-1` (Northern
  California) + `us-west-2` (Oregon) in the same
  hex; AWS `eu-west-1` (Ireland) + `eu-west-2`
  (London) in the same hex. This IS the panel's
  intent (continental aggregation), but if the
  audience expects per-cloud-region granularity,
  raise `hexbinResolution` to 5+ for sub-continental
  granularity OR use the markers companion with
  its `cluster` renderer for per-region collapse-
  expand at zoom.
- **Per-hex popup loses per-agent identity by design.**
  The hex aggregate is "47 tests across 12 agents in
  Western Europe"; clicking the hex does NOT reveal
  WHICH agents. For per-agent drill-down, pair this
  panel with the markers companion on the same
  Dashboard Studio panel via the BM-CT-1 layer
  contract — the markers layer becomes the per-
  agent drill-down, while the h3 layer remains the
  regional summary. Better Map's h3 renderer DOES
  revert to per-feature markers at building-
  resolution zoom levels (resolution 8+), so at
  high zoom the per-site popup reveals the
  individual datacenter (`agent_count` /
  `test_count` from §3); the per-agent identity
  remains a markers-companion responsibility.
- **No cross-panel normalisation.** Each h3 panel
  independently auto-scales its colour ramp to its
  own per-panel min/max. A panel showing 247 tests
  in Western Europe and 12 in APAC colours Western
  Europe deeply orange even though 247 might be the
  normal baseline for a heavy-cloud-agent tenant.
  For cross-tenant comparison panels, render an
  absolute-threshold colour ramp via the formatter's
  `colorStops` (or equivalent — see formatter schema
  for the exact property name) instead of relying
  on the auto-scale.
- **Agent location data quality is the trust
  boundary.** The `agent_lat` / `agent_lon` fields
  are populated by the ThousandEyes platform from
  either (a) customer-supplied location at agent
  registration, (b) auto-geocode from the agent's
  public IP, or (c) BGP-table reverse-lookup for
  cloud-hosted agents. The auto-geocode and BGP-
  lookup paths have well-documented inaccuracies
  (cloud-region centroid vs actual datacenter,
  ISP-NOC-coordinate fallback for residential
  agents) — a hex showing "12 agents in San
  Francisco" might include 8 agents whose true
  location is Sacramento or Reno because the
  geocode collapsed to the SF Bay Area centroid.
  This is acceptable for jurisdictional capacity
  planning (the audience cares about "is the West
  Coast covered?" not "is THIS specific city
  covered?") but document the limitation in the
  panel description.
- **No OT-safety boundary.** ThousandEyes agents
  measure IT services (HTTP, DNS, voice, BGP) —
  not OT / ICS protocols. The panel renders
  enterprise digital-experience telemetry only;
  no OT carve-out applies.
