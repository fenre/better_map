# Cisco Meraki (devices) — H3 hexbin

The fleet-density complement to the [meraki/markers](./markers.md)
recipe — same `meraki:devices` inventory feed, same `lng`-to-`lon`
rename, but aggregated into [H3](https://h3geo.org/) hexagonal
cells coloured by device COUNT. The hex layer answers the
strategic question **"where on the map is my Meraki fleet
densest?"** and surfaces under-served regions at a glance —
useful for a NetOps leadership view of a multi-site customer
that has grown by acquisition and may not realise just how
heavily concentrated the fleet is in the original HQ region.

## 1. Source description

Same `meraki:devices` sourcetype from the **Cisco Meraki
Add-on for Splunk** (`Splunk_TA_cisco_meraki`, Splunkbase ID
5580) as the companion [markers](./markers.md) recipe — the
TA polls the Meraki Dashboard REST API on a configurable
cadence and indexes one event per registered MR (wireless
AP) / MS (switch) / MX (security appliance) / MV (camera) /
MT (sensor) per polling cycle. Each event carries the
device's lat / lng (as configured in the Meraki Dashboard
map view) plus operational metadata (status, model, network
name).

**Why H3 hexbin for Meraki devices.** A markers view of a
500-device fleet works fine at building zoom but at world
zoom every site collapses to a single dense cluster — the
clustering renderer numbers them ("12", "47", "203") but the
operator loses the geographic-distribution story. H3 hexbin
COUNTS the devices inside each hex cell and colours the cell
by count, so an executive looking at the world view
immediately reads "we have 200 devices in the US Northeast,
80 in California, 12 in EMEA, 3 in APAC" without zooming or
clicking. This is the right layer for **leadership /
account-planning** views of the fleet, NOT for per-device
investigation (use markers for that).

**One-time setup before this recipe will return data:**

```bash
# Install + configure the TA, create the meraki index, register
# the organization, and enable the devices input. See the
# cisco-meraki-ta-setup skill for the full prerequisite list.
bash skills/cisco-meraki-ta-setup/scripts/setup.sh
bash skills/cisco-meraki-ta-setup/scripts/configure_account.sh \
  --name "MY_ORG" \
  --api-key-file /tmp/meraki_api_key \
  --org-id "<org_id>" \
  --region global \
  --auto-inputs \
  --index meraki
```

The setup steps are documentation only — they are NOT the
panel SPL. `scripts/check-recipe-schema.py` exempts §1
fences from the pipe-per-line gate; the panel SPL is in §2
and that one is enforced.

**Typical sourcetype / index:** `sourcetype="meraki:devices"`,
`index=meraki` (both are the TA defaults; if your install
renames the index, substitute below).

## 2. SPL recipe

```spl
index=meraki sourcetype="meraki:devices" earliest=-1h latest=now
| dedup serial sortby - _time
| where isnotnull(lat) AND isnotnull(lng)
| eval is_alerting=if(status=="alerting", 1, 0)
| eval is_offline=if(status=="offline" OR status=="dormant", 1, 0)
| rename serial AS id, lng AS lon
| stats count AS value, sum(is_alerting) AS alerting_count, sum(is_offline) AS offline_count BY id, lat, lon
| sort - value
| head 5000
```

Why this exact shape, line by line:

- **`index=meraki sourcetype="meraki:devices"`** — same TA
  defaults as the markers recipe. If your install renamed
  the index, substitute.
- **`earliest=-1h latest=now`** — covers 5–6 polling cycles
  (default 600 s). The `dedup serial sortby -_time` on the
  next line keeps the freshest snapshot per device.
- **`| dedup serial sortby -_time`** — one row per device,
  taking the newest snapshot. Same canonical pattern as the
  markers recipe.
- **`| where isnotnull(lat) AND isnotnull(lng)`** — drop
  devices not yet placed on the Meraki Dashboard map.
- **`| eval is_alerting=if(status=="alerting", 1, 0)` and
  `| eval is_offline=if(status=="offline" OR
  status=="dormant", 1, 0)`** — pre-compute per-device
  status flags as integers so the next `stats` can SUM them.
  This is the canonical Splunk pattern for "count rows
  matching a condition while also keeping a row-per-entity
  grain." The result: each hex cell will carry not just a
  device count but ALSO the count of alerting and offline
  devices inside it — drives the popup story
  ("47 devices · 3 alerting · 1 offline").
- **`| rename serial AS id, lng AS lon`** — adopt Better
  Map's canonical aliases. Same `lng` → `lon` gotcha as the
  markers recipe — Meraki's API uses three letters; Better
  Map's auto-detect uses two.
- **`| stats count AS value, sum(is_alerting) AS
  alerting_count, sum(is_offline) AS offline_count BY id,
  lat, lon`** — produces ONE row per device with `value=1`
  plus the alerting / offline flags. The hex layer then
  AGGREGATES (`hexbinAggregate: "sum"`) the `value` field
  across all rows in each hex cell, giving a per-cell device
  count. `alerting_count` and `offline_count` flow through
  as additional cell-level aggregates for the popup
  (Better Map sums numeric feature properties across cell
  members automatically per the hexbin layer contract).
- **`| head 5000`** — render budget. The H3 hexbin layer
  collapses 5000 devices into at most a few hundred visible
  hex cells at resolution 3, so the panel stays responsive
  even on the largest Meraki fleets.

## 3. Expected fields

| field          | type    | example        |
|----------------|---------|----------------|
| id             | string  | Q2XX-XXXX-XXXX |
| lat            | number  | 37.7749        |
| lon            | number  | -122.4194      |
| value          | integer | 47             |
| alerting_count | integer | 3              |
| offline_count  | integer | 1              |

All six fields appear in `expected_fields` in the frontmatter
and are cross-checked by `scripts/check-recipe-schema.py`.
Note that `value` here is the PER-DEVICE constant `1`; the
HEX-CELL `value` (the count of devices in the cell) is
computed client-side by the hex layer via
`hexbinAggregate: "sum"`.

## 4. Recommended formatter config

```json
{
  "pointRenderer": "h3",
  "hexbinAggregate": "sum",
  "hexbinResolution": 4,
  "hexbinOpacity": 0.7
}
```

Why this specific config:

- **`pointRenderer: "h3"`** — explicit pin to the H3 hexbin
  renderer. Same reason as the CIM Network Traffic h3 recipe:
  without the pin, the `auto` renderer might fall back to
  clustering below a row-count threshold and silently demote
  the panel from "fleet-density map" to "individual device
  map." Pinning makes the panel intent visible and stable.
- **`hexbinAggregate: "sum"`** — sum the per-row `value`
  field across all devices in each hex cell. With each row
  carrying `value=1`, the sum is the device count per cell
  — exactly what the panel question asks. The alternative
  `count` would also work here (since every row contributes
  exactly 1) but `sum` matches the formatter-schema enum
  values for cross-recipe consistency. NEVER use `mean` for
  this recipe — it would produce `mean(1) = 1` on every
  cell and render a flat colour, which is the wrong panel
  entirely.
- **`hexbinResolution: 4`** — H3 resolution 4 gives ~57,000
  cells globally, ~1,770 km² per cell — country-level
  resolution. This is the right grain for a NetOps fleet
  view because most enterprise Meraki deployments span
  ~10–50 distinct geographic regions, and resolution 4
  cleanly separates major metro areas without producing
  one ENORMOUS cell over "all of California." For a more
  granular "show me building-level density inside a single
  metro" view, raise to 5 (~252 km² per cell). For a more
  zoomed-out "show me continental concentration" view, drop
  to 3 (~7,800 km² per cell).
- **`hexbinOpacity: 0.7`** — slightly transparent so the
  underlying basemap labels show through; helps the
  leadership audience orient cells against city / region
  names without losing the colour signal.

## 6. Gotchas

- **`lng` vs `lon` is still the #1 mistake.** Same trap as
  the markers recipe — Meraki's REST API and the TA emit
  the longitude field as **`lng`** (three letters). Better
  Map's auto-detect only looks for `lon` / `longitude` /
  `long`. Forget the `rename lng AS lon` and the panel
  renders nothing; no error, just an empty map. The standing
  rule is "rename to canonical `lat`/`lon` at the END of the
  SPL, before `fields` or `stats BY lat, lon`".
- **`Splunk_TA_cisco_meraki` must be installed AND the
  `devices` input enabled.** This is NOT a vanilla-Splunk
  recipe — the TA is mandatory. The
  [`cisco-meraki-ta-setup` skill](https://github.com/fenre/better_map/blob/main/docs/recipes/meraki/h3.md)
  documents the complete install + configure flow.
- **Devices without a Dashboard location are invisible.**
  Same Meraki Dashboard contract as the markers recipe — a
  device without lat / lng will not render in either layer.
  The hex panel is even MORE forgiving than the markers
  panel because a single missing device in a 50-device hex
  cell barely shifts the count, BUT the inventory drift is
  still operationally meaningful. Add a companion panel
  (`index=meraki sourcetype="meraki:devices" earliest=-1h |
  dedup serial sortby -_time | where isnull(lat) OR
  isnull(lng) | stats count`) so the operator sees the
  missing-location count even though it does not show on
  the map.
- **Hex resolution vs fleet size.** Resolution 4 with < 50
  devices produces visually sparse cells (one device per
  cell looks identical to four devices per cell because
  the colour ramp doesn't reach the lower end of the scale
  at small data). Resolution 3 is better for small fleets.
  Resolution 5 is better for large fleets (5000+ devices)
  where the per-building density story matters. Rule of
  thumb: pick the lowest resolution that gives ≥ 5× as
  many devices as you have visible hex cells.
- **`value=1` per row is the right choice.** This recipe
  pre-computes `value=1` per device so the hex layer's
  `hexbinAggregate: "sum"` produces a clean device-count.
  The alternative — letting the hex layer count rows
  directly via `hexbinAggregate: "count"` — produces the
  same result on Meraki data BUT depends on the panel
  hot-pathing the row count instead of the value field,
  which is an implementation detail of the hex layer that
  could change in v1.8+. Setting `value=1` explicitly makes
  the intent reviewable AND future-proof.
- **`alerting_count` / `offline_count` cell aggregation.**
  Better Map's hex layer sums numeric feature properties
  across cell members per the hex-layer contract. So a hex
  cell with 47 devices, 3 of which are alerting and 1 of
  which is offline, will carry `alerting_count=3` and
  `offline_count=1` in its popup. To DRIVE the cell colour
  by these (e.g. "red cells = any device alerting in this
  region"), override `hexbinValueField` to `"alerting_count"`
  in the formatter config — the `auto` field selection
  picks `value`, the override lets the operator switch
  panel intent without rewriting the SPL.
- **Polling cadence vs panel auto-refresh.** Same as the
  markers recipe — the `devices` input polls every 600 s by
  default. A panel auto-refreshing every 30 s adds load
  without value. Tune panel refresh to 10 min for a better
  signal-to-load ratio.
- **MV camera privacy flag.** Same as the markers recipe —
  some EU deployments hide MV camera locations from the
  REST API for GDPR reasons. MV serials simply won't appear
  in the hex layer. To confirm: `index=meraki
  sourcetype="meraki:devices" productType="camera"
  earliest=-1h | dedup serial sortby -_time | where
  isnotnull(lat) | stats count`. If zero, you're hitting
  the privacy flag.
- **Time range.** The recipe hard-codes
  `earliest=-1h latest=now` to keep the dedup window small
  and fast. Replace with `earliest=$earliest$
  latest=$latest$` once you wire the recipe into a
  dashboard with a time-range input — but constrain the
  upper bound: a 30-day dedup is expensive AND not
  meaningful for an "is this fleet here NOW?" panel.
- **No CIM mapping.** Same as the markers recipe —
  `meraki:devices` is inventory data, not an event-stream
  sourcetype. The Cisco Meraki TA maps OTHER sourcetypes
  to CIM, but device inventory has no CIM home.
- **PII / GDPR posture.** This hex recipe is generally
  LOWER-risk than the markers recipe because hex cells
  collapse identifying device names ("AP - John Smith
  desk") into anonymous counts ("47 devices in this 1770 km²
  cell"). The popup still shows the cell-level aggregates,
  not per-device labels, so embedded-PII names do not leak
  through the hex panel.
- **No OT safety dependency.** Same as the markers recipe —
  Meraki devices are IT networking gear; MT sensors are IoT
  but not SIS-related. If your tenant integrates Meraki with
  an OT-zone monitoring program, route THOSE MT sensors to
  a dedicated `ot-datastreamer` recipe (per
  [`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
  Rule 6) rather than mixing them with the corporate
  Meraki inventory hex shown on this panel.
