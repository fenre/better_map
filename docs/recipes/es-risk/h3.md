# ES Risk-Based Alerting — H3 hexbin

The geographic-aggregation complement to the
[es-risk/markers](./markers.md) recipe — same `risk` index,
same `sum(risk_score) BY risk_object` RBA aggregator, same
ES Asset & Identity (A&I) framework lookup chain for
entity → home location, but rendered as H3 hexagonal cells
coloured by aggregate risk score rather than discrete
per-entity markers. The H3 layer surfaces **per-region
accumulated-risk PRESSURE** as hex cell colour intensity:
hot hexes indicate offices / datacenters where the most
risk-accumulating entities live; cool hexes indicate
regions where the workforce / fleet is currently quiet.
This is the natural shape when the SecOps question is
"which physical sites are accumulating the most risk
right now and let me drill into the leaders?" rather than
"show me each risky entity" (markers).

## 1. Source description

Same **Risk-Based Alerting (RBA)** data home as the
companion [markers](./markers.md) recipe — the `risk`
index, populated by the `action.risk = 1` adaptive-response
action attached to ES correlation searches. Each event
carries `risk_object`, `risk_object_type`, `risk_score`,
`risk_message`, `annotations.mitre_attack{}`, and
`source_search`. See the markers recipe §1 for the full
RBA primer.

**Why H3 hexbin for RBA risk.** A markers view at world
zoom collapses every site (corporate HQ, branch offices,
datacenter regions) into overlapping clusters that bury
the per-site comparison. A heatmap of risk-per-entity
would smear the site-level distinction into Gaussian blobs
that don't read as "site A has more risk than site B."
H3 hexbin AGGREGATES per-entity risk into per-site cells
with a clean comparable colour ramp — the right layer for
**SOC daily stand-up dashboards** where the operator
ranks sites and drills into the leader to see which
entities are contributing, NOT for per-entity
investigation (use markers for that).

**Heatmap vs H3 hexbin vs markers — when to choose which.**
For RBA specifically:
- **markers**: SOC analyst investigation, IR triage —
  "show me each risky entity individually."
- **H3 hexbin** (this recipe): SOC stand-up, leadership
  briefing — "which SITE is hottest and let me drill into
  the entities there."
- **heatmap**: not generally recommended for RBA — risk
  pressure is fundamentally per-entity-at-a-site, not
  smoothly geographically distributed. (If your tenant
  has thousands of entities spread continuously across a
  region with no clear site clustering, the heatmap
  shape could work; otherwise prefer markers or H3.)

**Typical sourcetype / index:** `index=risk` via the ``
`risk` `` macro. Requires `SplunkEnterpriseSecuritySuite`
plus `Splunk_SA_CIM` and an A&I lookup populated with
`lat` and `long` columns (the A&I CSVs DEFAULT-ship
without geographic columns — see the markers recipe §6
for the extension procedure and the geocode-by-IP
fallback).

## 2. SPL recipe

```spl
`risk` earliest=-24h latest=now
| stats sum(risk_score) AS total_risk BY risk_object, risk_object_type
| where total_risk >= 50
| lookup identity_lookup_expanded identity AS risk_object OUTPUT lat AS identity_lat, long AS identity_lon
| lookup asset_lookup_by_str src AS risk_object OUTPUT lat AS asset_lat, long AS asset_lon
| eval lat=coalesce(identity_lat, asset_lat)
| eval lon=coalesce(identity_lon, asset_lon)
| where isnotnull(lat) AND isnotnull(lon)
| eval value=total_risk
| rename risk_object AS id
| fields id, lat, lon, value, risk_object_type
| eventstats count AS entity_count BY lat, lon
| sort - value
| head 5000
```

Why this exact shape, line by line:

- **`` `risk` earliest=-24h latest=now ``** — `` `risk` `` is
  the ES macro that resolves to `index=risk` plus any
  optional risk index shards. Always use the macro, never
  hard-code `index=risk` — see the markers recipe §2 for
  the rationale.
- **`stats sum(risk_score) AS total_risk BY risk_object,
  risk_object_type`** — the canonical RBA aggregator,
  one row per entity with the entity's total accumulated
  risk over the window. The H3 hexbin recipe drops the
  `values(annotations.mitre_attack{})` and
  `values(source_search)` aggregates the markers recipe
  uses because per-cell rendering doesn't need per-entity
  techniques (the cell's contributing-entity drilldown
  panel can pull those on demand).
- **`where total_risk >= 50`** — signal-to-noise filter,
  matches the default RBA medium-priority threshold.
  Same advice as the markers recipe — match this to your
  tenant's RIR threshold.
- **Two `lookup` lines + `coalesce`** — same ES A&I
  fallback chain as the markers recipe. User-typed
  `risk_object` values resolve via the identity lookup;
  machine `risk_object` values resolve via the asset
  lookup; coalesce picks whichever hit.
- **`where isnotnull(lat) AND isnotnull(lon)`** — drop
  entities with no home location. Surface the count in
  a companion table panel so the operator sees the A&I
  geographic-extension gap.
- **`eval value=total_risk`** — **the H3 hexbin
  contract**. The layer expects a `value` field per row
  to aggregate across rows in the same cell. Setting
  `value` from total_risk makes the hex cell colour
  represent "total accumulated risk attributed to this
  region's entities" — exactly the SOC stand-up
  question.
- **`rename risk_object AS id`** — adopt Better Map's
  `id` alias. The entity name IS the unique drilldown
  key.
- **`eventstats count AS entity_count BY lat, lon`** —
  computes "how many distinct entities at this exact
  lat/lon" without losing the per-entity rows. This
  surfaces in the popup as the cell's contributing-
  entity count, helping the operator distinguish "one
  loud entity with 200 risk" from "ten entities with
  20 risk each" inside the same hot hex. **Note: this
  is a per-site count (entities sharing the same
  lat/lon), NOT a per-hex-cell count** — for the
  per-hex aggregate, see the cell-count gotcha in §6.
- **`head 5000`** — render budget. Most ES tenants
  accumulate <500 risk-object aggregates over 24 h
  above the default threshold; 5000 is comfortably
  above the worst-case noisy day.

## 4. Recommended formatter config

```json
{
  "pointRenderer": "h3",
  "hexbinAggregate": "sum",
  "hexbinResolution": 4,
  "hexbinOpacity": 0.7
}
```

Why this specific config:

- **`pointRenderer: "h3"`** — explicit pin to the H3
  hexbin renderer. The `auto` renderer never picks H3.
- **`hexbinAggregate: "sum"`** — **sum the per-entity
  risk scores per cell**. The cell colour reads as "the
  total accumulated risk attributed to entities in this
  region" — exactly the SOC stand-up question. Other
  valid aggregates per
  [`docs/_machine/formatter-schema.json`](https://github.com/fenre/better_map/blob/main/docs/_machine/formatter-schema.json):
  `max` (worst single entity per cell — useful for
  "which region has the single hottest entity?"),
  `avg` (average risk per entity per cell — useful for
  "where is the workforce average highest, normalised
  by site size?"), `count` (just entity density — but
  the markers companion with clustering already shows
  that).
- **`hexbinResolution: 4`** — **resolution 4** = ~17 km
  edge length per cell, ~1770 km² per cell. The right
  grain for an enterprise that has 10-50 distinct
  geographic sites (corporate offices + datacenters);
  resolution 4 cleanly separates major metro areas
  without producing one enormous cell over "all of
  California." For a more granular per-building view
  inside a single metro, raise to 5 (~252 km² per cell)
  or 6 (~36 km² per cell — building-level inside a
  campus). For a continental-zoom executive view, drop
  to 3 (~7800 km² per cell — region-level).
- **`hexbinOpacity: 0.7`** — same opacity as the other
  H3 recipes for cross-panel visual consistency.
- **`value` is the H3-layer-required aggregation
  field.** Better Map's `dataFitness.js` auto-picks
  `value` by name. No further formatter config needed.

## 6. Gotchas

- **A&I lookups need lat/lon columns — they do NOT
  ship that way.** Same blocker as the markers recipe.
  See [es-risk/markers](./markers.md) §6 for the
  extension procedure and the geocode-by-IP fallback.
- **H3 cell SAMPLE SIZE matters.** A hex cell with one
  entity inside it (a remote worker, a single-machine
  satellite office) shows that one entity's risk as
  the cell's total — misleading at world zoom (one
  outlier in a sparse region paints a whole cell red).
  The `entity_count` field is carried through to help
  the operator spot single-entity cells in the popup,
  but if your tenant has many sparse regions, add a
  per-cell pre-filter via the `splunkbase:h3` app:
  `| stats sum(total_risk) AS cell_total, dc(id) AS
  cell_entity_count BY <h3_index>` then
  `| where cell_entity_count >= 3` before the panel.
- **Aggregate function semantics.** `sum` totals risk
  across the cell — sensitive to one loud entity.
  `max` highlights the worst entity per cell — useful
  for "which region has my hottest entity?" but loses
  the per-region accumulation story. `avg` produces
  "average risk per entity per cell" — useful for
  comparing risk concentration across sites of
  different sizes. `count` reduces to entity density
  which the markers companion already shows. Pick
  `sum` for SOC-stand-up site totals; `max` for
  incident war rooms; `avg` for site-comparison
  panels.
- **`risk` index acceleration.** Same as the markers
  recipe — ES does NOT accelerate the `risk` index by
  default. A 24 h aggregate is usually fast enough; if
  your install generates >100k risk events per day,
  schedule a daily summary search.
- **Time range.** Hard-coded `earliest=-24h latest=now`
  matches the default RBA scoring horizon. Match the
  panel window to the RIR window in your tenant.
- **PII / GDPR posture.** Same as the markers recipe —
  `risk_object` values for `risk_object_type="user"`
  are by definition PII. The H3 hexbin panel is
  generally LOWER-risk than the markers companion for
  privacy-sensitive deployments because hex cells
  collapse identifying entity names into anonymous
  regional totals, but the popup may still expose
  entity-level data when the operator drills into a
  cell. Restrict via Splunk RBAC on the `risk` index
  for audiences without "see risky entities"
  authorisation, OR pre-hash the `risk_object` in SPL
  (`eval risk_object=md5(risk_object)`) — but note
  that hashing removes the drilldown affordance, so
  the panel becomes "where is risk concentrated?" only.
- **No OT safety dependency.** This recipe is pure IT
  identity-and-system risk. If your ES install ALSO
  scores OT-zone entities (passive DPI alerts from
  Cisco Cyber Vision feeding ES correlation searches),
  keep them in a SEPARATE recipe with
  `ot_safety_relevant: true` per
  [`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
  Rule 6 — a risky PLC needs a fundamentally different
  response than a risky laptop, and rendering a Level-0
  device's risk in the same hex cell as a corporate
  laptop's risk obscures the OT-vs-IT response
  distinction.

maintainer with REST auth to such a tenant should:

1. Verify the A&I extension is in place: `| inputlookup
   identity_lookup_expanded | where isnotnull(lat) |
   stats count`.
2. Confirm the `risk` index has data: `` | `risk`
   earliest=-24h | stats count ``.
3. Run the recipe SPL and confirm the panel renders
   hex cells with sensible per-cell risk totals.
4. Render the panel at resolutions 3, 4, 5 to confirm
   the hex grain matches the dashboard zoom level.
5. Run the markers companion side by side and confirm
   the hottest hex cells correspond to the highest-
   risk markers (sanity check on the `value`
   aggregation and the `head 5000` truncation).
6. Update the frontmatter to `status: verified`, fill
   in `verified_against` (include `splunk_app:
   "SplunkEnterpriseSecuritySuite"`), and submit a
   follow-up PR.
