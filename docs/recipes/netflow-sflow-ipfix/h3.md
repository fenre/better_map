# NetFlow / sFlow / IPFIX (flow records) — H3 hexbin

Aggregate per-flow byte volumes by geography into [H3](https://h3geo.org/)
hexagonal cells coloured by total traffic — answers "where on the
internet is my egress volume concentrated" at a glance, with cell
size that scales with hex resolution. The canonical NetOps /
SecOps macro-view for any team running flow collectors on edge
routers or load balancers.

## 1. Source description

**NetFlow** (Cisco, v5 / v9), **sFlow** (HPE / Aruba / Arista),
and **IPFIX** (the IETF-standard descendant of NetFlow v9) all
encode the same idea: a router or switch periodically emits a UDP
record summarising "between time A and time B, on this interface,
I forwarded N packets / B bytes of (src_ip, dst_ip, sport, dport,
protocol)". The records hit a collector (typically `Splunk_TA_netflow`,
or a side-car like `nfdump`/`pmacct` writing JSON to monitor:// or
HEC), are indexed, and become searchable in Splunk.

For a "where is my egress going" map we use IPFIX/NetFlow records
indexed by `Splunk_TA_netflow` (sourcetype `cisco:netflow` for
v9/IPFIX from Cisco devices; sourcetypes for other vendors are
documented in the
[`splunk-network-explorer` skill](https://github.com/fenre/better_map/blob/main/.cursor/rules/splunk-network-explorer.mdc)).

The recipe binds to events with `sourcetype="cisco:netflow"` (or
the equivalent for non-Cisco devices) indexed into the customer's
flow-data index (commonly `netflow`).

**Typical sourcetype / index:** `sourcetype="cisco:netflow"` /
`index=netflow`. Replace with `sourcetype="huawei:netstream"`,
`sourcetype="sflow"`, etc., to match your vendor.

**Why H3 hexbin for flow data:** raw flow records pre-aggregation
are millions per hour at a busy perimeter. Plotting one marker per
destination drowns the map in noise. Binning into H3 cells at
resolution 2-4 (continental scale) reduces 50k destinations to
~500-2000 hex cells, each coloured by the SUM of bytes inside it
— making aggregate trends obvious that per-marker views hide.

## 2. SPL recipe

```spl
index=netflow sourcetype="cisco:netflow"
| stats sum(bytes) AS bytes, dc(src_ip) AS flow_count BY dest_ip
| iplocation dest_ip
| where isnotnull(lat) AND isnotnull(lon)
| eval id=dest_ip, value=bytes
| fields id, lat, lon, value, dest_country, flow_count, bytes
```

What the pipeline does, stage by stage:

- **`stats sum(bytes) ... BY dest_ip`** — rolls up potentially
  millions of per-flow records into one row per destination IP,
  summing the byte counter and counting distinct sources as
  `flow_count`. Critical for performance: `iplocation` on
  un-aggregated flow data is a search-killer.
- **`iplocation dest_ip`** — Splunk's built-in geo-enrichment
  (MaxMind GeoLite2; ships with Splunk Enterprise / Cloud out of
  the box). Populates `lat`, `lon`, `Country` → aliased to
  `dest_country`. RFC-1918 destinations get null lat/lon; the
  `where` filter on the next line drops them.
- **`eval id=dest_ip, value=bytes`** — the H3 hexbin layer reads
  the per-row `value` field as the quantity to aggregate (summed
  across all rows that fall inside one hex cell). `id` is the
  per-row identifier for drilldown; for hex aggregation the per-
  row id is less meaningful but is retained for the optional
  "show me the rows inside this cell" drilldown.

The `fields` filter at the end is not strictly required but it
keeps the panel payload small — Better Map's WebSocket frame to the
browser carries every field, so trimming saves bandwidth on big
result sets.

Every `|` starts its own physical line per the SPL pipe-per-line
contract.

## 4. Recommended formatter config

```json
{
  "pointRenderer": "h3",
  "hexbinAggregate": "sum",
  "hexbinResolution": 3,
  "hexbinOpacity": 0.7
}
```

Why this config:

- **`pointRenderer: "h3"`** — pin the renderer to H3 hexbin
  explicitly. The `auto` renderer would also pick hexbin for
  large row counts, but pinning makes the panel intent visible
  in the frontmatter and prevents a row-count drop (e.g. during
  off-hours) from silently demoting the panel to individual
  markers, which then no longer carries the "macro-view" story.
- **`hexbinAggregate: "sum"`** — sum the per-row `value` field
  across all rows in each cell. The alternative `mean` is right
  for "average bandwidth per session" panels; `sum` is right for
  "total bytes shipped to this region" — which is the universal
  NetFlow story.
- **`hexbinResolution: 3`** — H3 resolution 3 gives ~12,392
  cells globally, ~7,800 km² per cell — i.e. continental-to-
  large-country scale. Resolution 4 (~1,770 km² per cell, ~57k
  global cells) is right for country-level visibility;
  resolution 5 (~252 km², ~400k cells) for city level. The
  layer reference documents the full grid.
- **`hexbinOpacity: 0.7`** — slightly transparent so the
  underlying basemap shows through; helps users orient cells
  without losing the colour signal. Drop to 0.5 if the basemap
  is dark and the palette is light; raise to 0.9 if cells are
  small and the user can't see colour differences.

## 6. Gotchas

- **NetFlow sampling.** Most production NetFlow exporters sample
  at 1:1000 or 1:4000 (one of every 1000-4000 flows is reported)
  for cost reasons. The `bytes` value in the indexed record is
  the SAMPLED value, NOT the wire-level total. If the panel must
  show "true total bytes", multiply by the sampling rate (the
  `Splunk_TA_netflow` event carries `sampling_interval`):
  `| eval value=bytes*sampling_interval`. If the panel is for
  relative comparison ("is destination A hotter than destination
  B"), the sample-rate cancels and the SPL above is correct.
- **sFlow vs NetFlow byte semantics.** sFlow's `bytes` is sampled
  packet counts × the sample interval × the per-flow average
  packet size; NetFlow v9/IPFIX reports per-flow octet totals
  directly. If you have a mix of both, normalise upstream in
  `transforms.conf` or you'll over-attribute volume to sFlow-
  reporting devices. The
  [`splunk-network-explorer` skill](https://github.com/fenre/better_map/blob/main/.cursor/rules/splunk-network-explorer.mdc)
  documents the normalisation pattern.
- **`iplocation` performance at scale.** Same warning as the
  Splunk Stream recipe: `iplocation` is per-row on a search-head;
  millions of rows × `iplocation` will dominate the panel cost.
  Always `stats` before `iplocation` (the SPL above does this).
  For panels that auto-refresh every minute against a busy
  perimeter, summary-index the post-`iplocation` result via a
  scheduled saved search and have the dashboard read the summary.
- **Hex resolution vs row count.** Resolution 3 with < 50 rows
  looks empty (most cells black). Resolution 5 with > 200,000
  rows starts pushing browser memory (200k+ hex cells, each with
  per-cell aggregate state). Rule of thumb: pick the lowest
  resolution that gives ≥ 10× as many ROWS as you have CELLS in
  the visible area — keeps the panel meaningful and fast.
- **No OT safety dependency, BUT.** Same posture as the
  splunk-stream recipe: NetFlow IS a sanctioned passive collection
  method for OT (no active probes; one of the methods called out
  in
  [`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
  Rule 1) but the resulting `dest_ip` set will contain Level-0/1/2
  PLCs and HMIs in an OT-instrumented environment. A hex-bin map
  of OT flows is fine for situational awareness; do NOT wire it
  to a SOAR or drilldown that could send a write back to those
  devices (Rule 3).
- **`Splunk_TA_netflow` deployment surface.** The TA is a Splunk-
  side parser; it expects pre-collected NetFlow records in
  `monitor://` or HEC. The collector itself (the thing that
  receives UDP NetFlow on port 2055 and writes the indexed
  format) is separate — Cisco's
  [Network Explorer skill](https://github.com/fenre/better_map/blob/main/.cursor/rules/splunk-network-explorer.mdc)
  documents the reference flow. Don't expect this recipe to "just
  work" against a stock Splunk install with no collector wired in.

## Verification status

`status: unverified` in the frontmatter — the SPL is structurally
sound and follows the documented NetFlow / sFlow / IPFIX patterns
(see references) but it has not been dispatched against a real
`cisco:netflow` index in the v1.7-prep development cycle (the lab
tenant does not have a NetFlow collector deployed). A maintainer
with a Splunk tenant carrying NetFlow data should:

1. Run the SPL against `index=netflow sourcetype="cisco:netflow"`
   (adjust the index/sourcetype names to match the install — sFlow
   sources commonly use `sourcetype="sflow"`).
2. Confirm the panel returns ≥ 100 rows over a 1-hour window with
   all six documented fields populated.
3. Render the panel at resolutions 2, 3, 4 to confirm the panel
   degrades gracefully (Better Map's H3 layer should never show
   browser jank or per-cell errors). If it does, drop a
   reproduction case in the
   [hexbin layer source](https://github.com/fenre/better_map/blob/main/better_map/appserver/static/visualizations/better_map/src/lib/layers/hexbin.js)
   PR queue.
4. Update the frontmatter to `status: verified`, fill in
   `verified_against` (e.g. "Splunk Enterprise 10.0 with
   Splunk_TA_netflow 4.0.0 against a 4-edge-router NetFlow v9
   collector"), and submit a follow-up PR. The CI gate
   `scripts/check-recipe-schema.py` will accept the change without
   touching the schema.
