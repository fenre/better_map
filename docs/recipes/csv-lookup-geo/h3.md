# CSV lookup (geo points) — H3 hexbin

Aggregate per-point values from a customer-owned CSV lookup into
[H3](https://h3geo.org/) hexagonal cells coloured by total or mean
value — answers "where on the map are my incidents / assets / events
concentrated" for any dataset small enough to ship as a CSV (typical
range: 100 - 10,000 points, optionally up to 100,000 with KV-Store
migration per §6 Gotchas). The canonical "macro-view of a
geographic dataset" recipe when the source is a CSV rather than a
live event stream.

## 1. Source description

A **CSV lookup** is the simplest possible Splunk external-data
source: a file on disk under `<app>/lookups/<name>.csv`, exposed
to SPL via a `transforms.conf` stanza, queried with
`| inputlookup <name>`. CSV lookups are ideal for static
geographic datasets that an analyst maintains by hand or imports
from a system of record (ServiceNow incidents, Salesforce
accounts, asset registers, customer-curated point-of-interest
lists, historical case archives).

Why H3 hexbin instead of individual markers:

- **Visual density.** A CSV with 5,000 incidents plotted as
  markers creates "marker soup" — the eye can't separate clusters
  from noise. H3 hexbin at resolution 4-5 reduces that to 200-800
  hexagons, each shaded by a per-cell aggregate (sum, mean, max,
  count).
- **Area-neutral aggregation.** Unlike country / state choropleth
  (which is biased by the modifiable areal unit problem — large
  states like California always look "dominant" because of their
  size), H3 cells are equal-area within a resolution. A cell with
  10 incidents in San Francisco shades the same as a cell with 10
  incidents in rural Wyoming.
- **Smooth resolution tuning.** H3 has 15 resolutions, each ~7×
  smaller than the last. The panel author picks the resolution
  that matches the panel's geographic scope (resolution 3 for
  continental, 4-5 for country, 6-7 for metro, 8+ for city block).

The recipe binds to a lookup named `incidents.csv` (rename to match
your install) with the columns `incident_id`, `lat`, `lon`,
`severity`, `incident_category`. The `severity` column drives the
hexbin value; the `incident_category` flows through as a feature
property for popups.

**Typical sourcetype / index:** none — `| inputlookup` runs against
the CSV directly, no event ingestion involved. (For incident
datasets imported nightly from an ITSM system, the import pipeline
is `| sendto-csv` from the ITSM modular input + a scheduled report
that does `| outputlookup incidents.csv`; that pipeline is
out-of-scope for this recipe.)

**One-time setup** (skip if your lookup already exists):

```spl
| makeresults
| eval incident_id="INCIDENT-2025-12834", lat=37.7749, lon=-122.4194,
       severity=3, incident_category="service_outage"
| append [
  | makeresults
  | eval incident_id="INCIDENT-2025-12835", lat=40.7128, lon=-74.0060,
         severity=2, incident_category="network_degradation"]
| append [
  | makeresults
  | eval incident_id="INCIDENT-2025-12836", lat=41.8781, lon=-87.6298,
         severity=4, incident_category="security_event"]
| fields - _time
| outputlookup incidents.csv
```

(The one-time setup is the only place `| makeresults` is allowed in
this recipe — it is bootstrap data, not panel data. Per ROADMAP §1a
and the Splunk SPL anti-pattern rules, `| makeresults` is BANNED
in panel SPL because it bypasses time-range filtering and can't be
distributed.)

After the `| outputlookup`, register the lookup in
`transforms.conf` (already done if you use the Splunk Web lookup
UI). See the [Splunk lookups
skill](https://github.com/fenre/better_map/blob/main/.cursor/skills/splunk-lookups/SKILL.md)
for the full transforms.conf stanza pattern.

## 2. SPL recipe

```spl
| inputlookup incidents.csv
| where isnotnull(lat) AND isnotnull(lon)
| rename incident_id AS id, severity AS value
| fields id, lat, lon, value, incident_category
| sort - value
| head 10000
```

What the pipeline does, stage by stage:

- **`| inputlookup incidents.csv`** — pulls every row of the CSV
  into the search pipeline. CSV lookups are cached in memory on
  the search head; this is sub-millisecond for < 10k rows.
- **`| where isnotnull(lat) AND isnotnull(lon)`** — defensive
  filter for rows where geocoding upstream failed. Without it,
  rows with null coordinates would be silently dropped by the
  hexbin layer with no diagnostic.
- **`| rename incident_id AS id, severity AS value`** — Better
  Map's hexbin layer hardcodes `idProperty: 'id'` and uses the
  per-row `value` field as the quantity to aggregate (summed,
  averaged, or counted across all rows in a cell per the
  formatter's `hexbinAggregate` option).
- **`| fields id, lat, lon, value, incident_category`** — trim
  to the five fields the panel actually consumes. The
  `incident_category` flows through for popup labels.
- **`| sort - value | head 10000`** — defensive cap. The hexbin
  layer can handle ~10k input rows efficiently; above that, see
  §6 Gotchas for the KV-Store migration path.

Every `|` starts its own physical line per the SPL pipe-per-line
contract in `splunk-conf-and-spl.mdc`.

## 4. Recommended formatter config

```json
{
  "pointRenderer": "h3",
  "hexbinAggregate": "sum",
  "hexbinResolution": 4,
  "hexbinOpacity": 0.7
}
```

Why this config:

- **`pointRenderer: "h3"`** — pin the renderer to H3 hexbin
  explicitly. The `auto` renderer would also pick hexbin for
  large row counts, but pinning makes the panel intent visible
  in the frontmatter and prevents a row-count drop (e.g., after
  archiving old incidents) from silently demoting the panel to
  individual markers — which then no longer carries the
  "macro-view of incident density" story.
- **`hexbinAggregate: "sum"`** — sum the per-row `value` field
  across all rows in each cell. For incident severity (1 = low,
  5 = critical), sum gives "total severity weight per cell" —
  high-severity outliers stand out. Use `mean` if value is a
  rate or percentage (e.g., uptime %); use `count` to ignore
  `value` entirely and show "how many incidents per cell";
  use `max` to show "what is the worst-severity incident in
  each cell".
- **`hexbinResolution: 4`** — H3 resolution 4 gives ~1,770 km²
  per cell (~57k cells globally) — i.e., country-to-large-state
  scale. For US-state-sized aggregation, use resolution 3
  (~12,392 cells globally, ~7,800 km² per cell); for metro
  scale, use resolution 6 (~36 km² per cell, ~14M cells
  globally). The layer reference documents the full grid.
- **`hexbinOpacity: 0.7`** — slightly transparent so the
  underlying basemap shows through; helps users orient cells
  without losing the colour signal. Drop to 0.5 if the basemap
  is detailed (sat imagery, terrain); bump to 0.9 for a
  monochrome basemap where opacity matters less.

## 6. Gotchas

- **CSV lookups are NOT distributed.** Splunk replicates lookup
  files to search peers, but the search-head executes
  `| inputlookup` locally — no map-reduce parallelism. For
  datasets above ~10k rows, the recipe noticeably slows panel
  load. Migration path: dump the CSV into a KV-Store collection
  (see [`kvstore-latlon/markers`](https://fenre.github.io/better_map/recipes/kvstore-latlon/markers/)
  and [`kvstore-latlon/heat`](https://fenre.github.io/better_map/recipes/kvstore-latlon/heat/)
  for the KV-Store collection-creation pattern) and query with
  `| inputlookup <collection>` — same SPL, distributed execution.
  Rule of thumb: < 10k rows → CSV; 10k - 100k → KV-Store with an
  unindexed key; > 100k → KV-Store with `accelerated_fields`
  (per the `splunk-lookups` skill).
- **Null lat/lon rows kill the panel silently.** If the CSV has
  rows with missing coordinates (incomplete geocoding upstream,
  imported records that lack a known address, etc.), the hexbin
  layer drops them without a diagnostic. The defensive
  `| where isnotnull(lat) AND isnotnull(lon)` in §2 catches
  this — keep it even if you "know" your CSV is clean, because
  the next import may break that invariant.
- **`value` field must be a number, not a string.** CSV columns
  default to string type unless cast. The recipe's `severity`
  column is implicitly numeric in the bootstrap SPL because of
  `eval severity=3`; if your CSV was authored by a human and
  loaded via `outputlookup` from an `eval severity="3"` (quoted),
  the hexbin layer's aggregation will silently fail. Defensive
  fix: add `| eval value=tonumber(value)` before the hexbin
  layer consumes it.
- **H3 resolution choice changes the story.** Resolution 4 cells
  in a city aggregate too much (the whole San Francisco peninsula
  becomes one cell). Resolution 7 cells across a continent
  aggregate too little (each city becomes thousands of tiny
  cells). The right resolution depends on the panel's
  geographic scope: continental dashboards → 3, country
  dashboards → 4-5, metro dashboards → 6-7, city blocks → 8+.
  When in doubt, prototype at resolution 5 and adjust ±1 based
  on visual readability.
- **Hexbin vs supercluster vs heat — pick the right layer.** This
  recipe's H3 hexbin is one of three macro-view options for point
  data; pick by use case:

  | Layer        | Best for                                                | Loses                                           |
  |--------------|---------------------------------------------------------|-------------------------------------------------|
  | H3 hexbin    | Area-neutral density, geographic aggregation            | Per-point drilldown (drills into a cell, not a row) |
  | Supercluster | Preserving per-point drilldown affordance               | Visual density at low zoom (clusters merge)     |
  | Heat         | Smooth kernel-density visualization, anomaly hot-spots  | Per-point drilldown, hard cell boundaries       |

  This recipe uses H3 because the question is "where are
  incidents concentrated geographically" — a cell-aggregate
  question. For "which specific incidents are clustered together
  at city X" use the supercluster recipe; for "where are
  smooth density anomalies" use the heat recipe.
- **No OT safety dependency.** This recipe ingests bootstrap
  CSV data and aggregates it by geography. The CSV may carry
  records DERIVED from OT systems (e.g., per-site equipment
  failure records rolled up from Level-0/1/2 telemetry into
  a Level-3 or Level-4 incident-management summary), but the
  recipe itself never reads from a Level-0/1/2 source. The
  OT-safety boundary lives in the upstream pipeline that
  produces the CSV, not in this recipe.

## Verification status

`status: unverified` in the frontmatter — the SPL is structurally
sound and uses only Splunk built-ins (`inputlookup`, `where`,
`rename`, `fields`, `sort`, `head`). The hexbin aggregation
behaviour is covered by Better Map's own `hexbin` module unit
tests, but the end-to-end "this recipe's CSV renders a hexbin
panel in a Splunk Dashboard Studio install" path has not been
dispatched against the v1.7-prep lab tenant in this PR because
(a) non-interactive admin auth is not present in the agent
workspace, and (b) the lab tenant does not carry a populated
`incidents.csv`. A maintainer with REST auth should:

1. Populate `incidents.csv` with the bootstrap SPL in §1 (or any
   real geographic point dataset with `lat`/`lon` columns and a
   numeric value column).
2. Run the recipe SPL and confirm rows are returned with non-null
   `lat`, `lon`, `value`.
3. Drop the panel into a Dashboard Studio dashboard with the
   formatter JSON in §4 and confirm hexagons render with
   colour-by-value.
4. Update the frontmatter to `status: verified`, fill in
   `verified_against`, and submit a follow-up PR.
