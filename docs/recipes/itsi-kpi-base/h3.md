# ITSI service health — H3 hexbin

The geographic-aggregation complement to the
[itsi-kpi-base/markers](./markers.md) and
[itsi-kpi-base/heat](./heat.md) recipes — same `itsi_summary`
⋈ `itsi_services` join, same `SHKPI-`-prefixed service-health
filter, same `info_lat` / `info_lon` geo-attribute prerequisite,
but rendered as H3 hexagonal cells rather than markers or a
heat surface. The H3 layer surfaces **per-region service-
health PRESSURE** as hex cell colour intensity: hot hexes
indicate continental jurisdictions / metro regions with the
highest aggregate UNHEALTHY-SERVICE-COUNT; cool hexes
indicate quiet regions. This is the natural shape for a
**multi-region SRE board view** (the question is "which
geographic region's services are degraded right now, with
hard hex borders for jurisdictional reporting?" rather than
"which individual service should I investigate" — use markers
for that, or "where is pressure smoothly concentrated" — use
heat for that).

Completes the **itsi-kpi-base source-row triplet** — markers
(wave 11), heat (wave 18), H3 hexbin (this wave) — all three
layers coexisting via the BM-CT-1 layer contract on the same
Dashboard Studio panel. This is the **13th source-row triplet
completed in the matrix** (after cim-alerts, cim-authentication,
cim-network-traffic, cim-performance, csv-lookup-geo,
cyber-vision, es-risk, kvstore-latlon, meraki,
netflow-sflow-ipfix, ot-datastreamer, splunk-stream — leaving
only `thousandeyes` as the last triplet target).

## 1. Source description

Same Splunk **IT Service Intelligence (ITSI)** `itsi_summary`
index + `itsi_services` KV-Store collection as the
[markers](./markers.md) and [heat](./heat.md) companions. The
recipe assumes the same prerequisite — that the operator has
populated `info_lat` + `info_lon` as custom service attributes
via the ITSI UI (Configuration → Service Templates → custom
attributes) or via the ITSI REST API. Without that, all three
recipes return zero rows.

**Why H3 hexbin for ITSI service health.** A markers view
at world zoom collapses dense per-datacenter service clusters
into overlapping circles that hide individual service
identity behind visual noise. A heat view solves the density
problem with a smooth Gaussian gradient but the heat blobs
have NO hard borders — board-level reporting that needs
"how many unhealthy services in the EU jurisdiction this
quarter?" cannot answer that from a Gaussian gradient. An
H3 hexbin AGGREGATES the underlying services into regular
hexagonal cells (Uber's open H3 grid system) and lets the
viewer count "how many unhealthy services live in THIS
hex." The continental-scale resolution-3 cells map roughly
to "Western Europe" / "US East Coast" / "Southeast Asia" —
exactly the granularity an SRE / governance board uses to
think about geographic blast-radius.

**Typical sourcetype / index:** `index=itsi_summary`
(same as the companion recipes). The KV-Store lookup uses
the same `itsi_services` collection (or the built-in
`` `itsi_services` `` macro if exposed). The H3 cell id
is computed by Better Map's h3 layer renderer at render time
from the `lat` / `lon` columns; the SPL does NOT pre-compute
H3 cells (the renderer's resolution selector is the formatter
config option `hexbinResolution`, not a fixed SPL choice —
keeping resolution-tuning in the formatter avoids re-running
SPL when an operator wants to switch from continental
resolution 3 to country resolution 5 mid-investigation).

## 2. SPL recipe

```spl
index=itsi_summary kpi_id="SHKPI-*" entity_key="N/A" earliest=-15m latest=now
| stats latest(alert_level) AS alert_level BY itsi_service_id
| lookup itsi_services _key AS itsi_service_id OUTPUT info_lat AS lat, info_lon AS lon
| where isnotnull(lat) AND isnotnull(lon)
| eval alert_level=tonumber(alert_level)
| eval is_unhealthy=if(alert_level >= 3, 1, 0)
| stats sum(is_unhealthy) AS unhealthy_services, count AS total_services BY lat, lon
| eval value=unhealthy_services
| eval id=lat . "_" . lon
| fields id, lat, lon, value, unhealthy_services, total_services
| sort - value
| head 5000
```

Why this exact shape, line by line:

- **`index=itsi_summary kpi_id="SHKPI-*" entity_key="N/A"`** —
  same prefix filter as the [markers companion §2](./markers.md#2-spl-recipe)
  and [heat companion §2](./heat.md#2-spl-recipe). `SHKPI-`
  is ITSI's prefix for synthetic service-health KPIs (one
  per service); `entity_key="N/A"` filters out per-entity
  rows.
- **`earliest=-15m latest=now`** — same 3× KPI-cadence
  window as the markers / heat companions (service-health
  roll-ups emit every 5 min by default). Do NOT widen for
  the h3 layer specifically — the panel question is "which
  region is unhealthy RIGHT NOW?" not "over the last hour?".
- **`stats latest(alert_level) AS alert_level BY itsi_service_id`** —
  drop everything except the freshest `alert_level` per
  service. The h3 recipe DOESN'T need `health_score` or
  `service_title` because per-cell aggregation discards
  per-service identity by design (the value rendered IS
  the cell-level unhealthy count).
- **`lookup itsi_services ... OUTPUT info_lat AS lat, info_lon AS lon`** —
  same join as markers / heat. The h3 recipe pulls THE
  FEWEST fields of the three layer recipes (no
  `identifying_name`, no `service_title`) because hex
  aggregation discards everything except the geographic
  coordinates.
- **`where isnotnull(lat) AND isnotnull(lon)`** — drop
  services without geographic attribution (same as
  markers / heat). Surface the dropped count in a
  companion table panel so the ITSI admin sees the
  attribute gap (and use the same per-tenant DC-fallback
  pattern from the markers Gotchas if `info_lat` / `info_lon`
  are sparsely populated).
- **`eval alert_level=tonumber(alert_level)`** — string-to-
  number coercion. Without this the `>= 3` comparison would
  silently misclassify ("10" < "3" lexicographically). Same
  defensive pattern as the heat companion.
- **`eval is_unhealthy=if(alert_level >= 3, 1, 0)`** — the
  per-service binary flag. `alert_level >= 3` is the
  conventional "Medium-or-worse" threshold (3=Medium,
  4=High, 5=Critical); levels 0-2 (Info / Normal / Low)
  count as "healthy enough." Adjustable per panel — see
  §6 Gotchas for the threshold-as-panel-definition
  contract that matches the heat companion.
- **`stats sum(is_unhealthy) AS unhealthy_services, count AS total_services BY lat, lon`** —
  THE pivotal line. Switch from per-service to per-site
  aggregation. `sum(is_unhealthy)` counts how many
  services at this (`lat`, `lon`) are in Medium+ severity
  right now; `count` counts the total services at the
  site (the denominator if you want to render a
  percentage instead of an absolute count via a panel-
  specific `| eval value=round(100*unhealthy_services/total_services, 1)`
  rewrite). One row per geographic site; the H3 renderer
  then aggregates THESE rows into hex cells based on
  `hexbinResolution`.
- **`eval value=unhealthy_services`** — adopt Better Map's
  `value` alias for the h3-layer aggregate field. The
  default hexbinAggregate is `sum`, so the h3 renderer
  computes `cell_value = sum(value)` per hex — exactly
  the cell-level unhealthy-service count this panel needs.
  To render the cell-level service-count instead, swap to
  `eval value=total_services` and the per-cell sum becomes
  "total services in this jurisdiction." To render the
  cell-level unhealthy percentage, swap to
  `eval value=round(100*unhealthy_services/total_services, 1)`
  AND set `hexbinAggregate=avg` so the cell value is
  the mean per-site percentage rather than a sum.
- **`eval id=lat . "_" . lon`** — h3 layer doesn't strictly
  need `id` (per-feature identity is moot for a cell
  aggregate), but the formatter `idField` enables the
  per-site hover popup BEFORE the cell aggregation kicks
  in at low zoom (Better Map's h3 renderer reverts to
  per-feature markers at building-resolution zoom levels).
  The `lat_lon` concatenation is stable because two sites
  cannot share both lat AND lon.
- **`fields ...`** — explicit projection. Drops
  `alert_level` (already used in `is_unhealthy`) and
  transient lookup columns. `unhealthy_services` and
  `total_services` are carried so the per-site popup (at
  high zoom) can show "site DC-AMS-01: 7 of 23 services
  unhealthy" alongside the cell aggregate.
- **`sort - value`** — most-stressed sites first (matters
  for the companion "Top 10 sites" table panel; the h3
  renderer itself is row-order-agnostic because it
  re-aggregates by hex).
- **`head 5000`** — safety net. Largest ITSI installs run
  500 services across 20-40 datacenters; 5000 is 100× the
  realistic upper bound on per-site rows.

Note every `|` starts its own physical line per the SPL
pipe-per-line contract.

## 3. Expected fields

| field              | type    | example          |
|--------------------|---------|------------------|
| id                 | string  | 8a283082a677fff  |
| lat                | number  | 53.5511          |
| lon                | number  | 9.9937           |
| value              | number  | 7                |
| unhealthy_services | integer | 7                |
| total_services     | integer | 23               |

All six fields appear in `expected_fields` in the frontmatter
and are cross-checked by `scripts/check-recipe-schema.py`.
`value` is the h3-layer-required aggregation field (drives
`hexbinAggregate`); `unhealthy_services` and `total_services`
are carried for the per-site popup at high zoom (where the
h3 renderer reverts to per-feature markers). The `id` shown
in the example column is illustrative — the actual SPL
derives `id = lat . "_" . lon`; the H3 cell id itself
(`8a283082a677fff`-style) is computed at render time by the
h3 layer based on the formatter's `hexbinResolution`.

## 4. Recommended formatter config

```json
{
  "pointRenderer": "h3",
  "hexbinAggregate": "sum",
  "hexbinResolution": 3,
  "hexbinOpacity": 0.7
}
```

Why this specific config:

- **`pointRenderer: "h3"`** — explicit pin to the h3
  renderer. The `auto` renderer switches to h3 above
  ~200 features but the per-site aggregation in §2
  often returns 20-40 datacenter rows; without the
  explicit pin the renderer would stay on markers
  and miss the jurisdictional aggregation the panel
  is designed for.
- **`hexbinAggregate: "sum"`** — the default cell
  aggregate. `sum(value)` per hex cell gives the
  total unhealthy-service count in this jurisdiction
  ("Western Europe: 12 unhealthy services across
  all monitored datacenters in this hex"). For the
  cell-level percentage variant (see §2 commentary),
  swap to `"avg"` so the cell value is the mean of
  per-site percentages rather than a sum of counts.
- **`hexbinResolution: 3`** — continental resolution.
  Resolution 3 cells span ~1500km² and map roughly to
  "Western Europe" / "US East Coast" / "Southeast
  Asia" — ideal for the board-level "which continental
  jurisdiction is in the orange?" question this panel
  answers. Resolutions 4-5 (~200km² / ~30km²) are
  right for country-level views; resolutions 6-7
  (~5km² / ~1km²) for metro / city views; resolutions
  8-9 for per-building views. Tune per panel based on
  the audience: a global SRE leadership panel stays at
  3; a country-team panel might go to 5; a single-
  datacenter operations panel to 7.
- **`hexbinOpacity: 0.7`** — matches the
  [es-risk/h3](../es-risk/h3.md) and
  [kvstore-latlon/h3](../kvstore-latlon/h3.md) recipes.
  At 1.0 the hex fully occludes city labels and
  country borders underneath; at 0.5 the cells are
  washed out against bright underlay tiles; 0.7 is
  the sweet spot for the SRE / governance audience
  that needs to read BOTH the hex aggregate value AND
  the country / region context underneath.
- **`value` drives the hex aggregate automatically.**
  The h3 renderer auto-picks the `value` field by name
  (per Better Map's `dataFitness.js` field aliasing).
  If you rename `value` in the SPL, also set the
  formatter's `hexbinValueField` option (or whichever
  name the formatter schema uses — check
  [`docs/_machine/formatter-schema.json`](https://github.com/fenre/better_map/blob/main/docs/_machine/formatter-schema.json)).

## 6. Gotchas

- **`info_lat` / `info_lon` ITSI custom attributes are a
  prerequisite, identical to the markers / heat companions.**
  ITSI services do NOT carry lat/lon natively — the operator
  must populate these as custom service attributes via the
  ITSI UI (Configuration → Service Templates → custom
  attributes) or the ITSI REST API
  (`/servicesNS/-/SA-ITOA/itoa_interface/service/<key>`,
  add `{ "info_lat": "53.5511", "info_lon": "9.9937" }` to
  the service body). For an install without populated
  `info_lat` / `info_lon`, see the markers Gotchas section
  for the three-step migration pattern (CSV import via
  service template variables, or a one-time REST script).
  Without this prerequisite, the h3 layer renders zero hexes.
- **`alert_level >= 3` threshold is a panel-level definition,
  identical to the heat companion.** The recipe uses
  `>= 3` (Medium+) as the panel default; document this in
  the dashboard description so operators understand what
  "unhealthy" means in their context. Adjust per panel:
  - `>= 2` for a panel that flags Low-or-worse (extremely
    noisy in a healthy environment; useful as a "any
    degradation at all" exec view)
  - `>= 4` for a panel that flags High-or-Critical only
    (less noisy; the right shape for an executive
    leadership view when you want "everything's fine
    unless it's really bad")
  - `>= 5` for a Critical-only panel (the right shape
    for an emergency response dashboard that highlights
    only sites with active critical incidents)
- **H3 cells aggregate ACROSS datacenters in the same
  region.** Resolution 3 (~1500km²) puts Frankfurt and
  Amsterdam in the same hex, US East coast datacenters
  (Northern Virginia + DC + New Jersey + Washington DC)
  in the same hex, all UK datacenters in the same hex.
  This IS the panel's intent (jurisdictional aggregation),
  but if the audience expects per-datacenter granularity,
  use the heat or markers companions or raise
  `hexbinResolution` to 5+ for country-level granularity.
  Document the resolution choice in the panel description.
- **Per-hex popup loses per-service identity by design.**
  The hex aggregate is "12 unhealthy services in Western
  Europe"; clicking the hex does NOT reveal WHICH
  services are unhealthy. For per-service drill-down,
  pair this panel with the markers companion on the same
  Dashboard Studio panel via the BM-CT-1 layer contract —
  the markers layer becomes the per-service drill-down,
  while the h3 layer remains the regional summary.
  Better Map's h3 renderer DOES revert to per-feature
  markers at building-resolution zoom levels (resolution
  8+), so at high zoom the per-site popup reveals the
  individual datacenter (`unhealthy_services` /
  `total_services` from §3); the per-service identity
  remains a markers-companion responsibility.
- **No cross-panel normalisation.** Each h3 panel
  independently auto-scales its colour ramp to its own
  per-panel min/max. A panel showing 12 unhealthy services
  in Western Europe and 2 in US East Coast colours Western
  Europe deeply orange even though 12 might be perfectly
  normal for a fleet-of-1000-services tenant. For cross-
  tenant comparison panels, render an absolute-threshold
  colour ramp via the formatter's `colorStops` (or
  equivalent — see formatter schema for the exact
  property name) instead of relying on the auto-scale.
- **Resolution-3 hex coordinates are NOT GDPR-relevant.**
  A resolution-3 hex covers entire continental sub-regions
  (~1500km²), so the rendered cell value cannot identify
  any individual datacenter — much less any individual
  service or operator. This is the SAFEST of the three
  ITSI layer recipes from a GDPR / data-residency
  perspective: markers reveal per-service identity; heat
  reveals per-site density (still useful for an attacker
  mapping the fleet); h3 at resolution 3 reveals only
  jurisdictional aggregates. Raising resolution to 7+
  (per-building) reverses this — review the resolution
  choice against the panel's intended audience.
- **No time parameterisation needed.** The recipe
  hard-codes `earliest=-15m latest=now`; the panel is
  "current state" by definition. To render a 24-hour
  rolling aggregate (e.g. "which region accumulated
  the most unhealthy-service-minutes in the last 24h?")
  the SPL needs a fundamentally different shape —
  `eventstats` over a 24h window with a
  `time-of-unhealthy` per-service running total. That's
  a separate recipe candidate, not a parameter tweak.
- **No OT-safety boundary for IT-only ITSI installs.**
  This recipe assumes ITSI tracks IT services only
  (`Splunk` apps, business-services, customer-facing
  applications). If ITSI tracks BOTH IT services AND OT
  / ICS safety-related services in the same instance,
  the panel MUST filter out the OT services before
  per-site aggregation:
  `kpi_id="SHKPI-*" entity_key="N/A" itsi_service_id!="<OT_service_ids>"`
  per the [ot-safety](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
  rule (Rule 1 + Rule 5 — SIS services belong in a
  dedicated layer with their own `ot_safety_relevant:
  true` flag because hex aggregation does NOT preserve
  per-service safety distinctions).
