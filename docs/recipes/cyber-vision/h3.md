# Cisco Cyber Vision — H3 hexbin

The geographic-aggregation complement to the
[cyber-vision/markers](./markers.md) recipe — same
Cisco Cyber Vision components + vulnerabilities
streams, same operator-maintained
`cybervision_sites.csv` for physical lat / lon, but
rendered as H3 hexagonal cells coloured by aggregate
OT-asset count per region rather than discrete
per-asset markers. The H3 layer surfaces **per-site
OT asset DENSITY** (and optionally aggregate CVE
exposure) as hex cell colour intensity: hot hexes
indicate densely-populated production sites; cool
hexes indicate sparse or remote facilities. The
natural shape when the plant-OT-leadership question
is "which SITES have the largest OT footprint, and
where is our CVE exposure concentrated regionally?"
rather than "show me each PLC individually"
(markers companion).

Strict adherence to the
[`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
boundary, identical to the markers companion: Cyber
Vision is the **reference passive-DPI design** per
Rule 1; this recipe consumes its already-passive
metadata stream without ever querying the OT zone.

## 1. Source description

Same Cisco Cyber Vision passive DPI source as the
[cyber-vision/markers](./markers.md) companion — see
the markers recipe for the full background on Cyber
Vision sensors, the four sourcetypes
(`components`, `flows`, `events`, `vulnerabilities`),
and the operator-maintained `cybervision_sites.csv`
lookup contract.

**Why H3 hexbin for Cyber Vision.** The markers view
is the right shape for OT-asset-team investigation
("which exact PLC at FLOOR3-PAINT is exposed?") and
for site-level visibility ("show me every asset at
the Houston plant"). It's the wrong shape for
multi-site plant-leadership situational awareness
("which of our 27 manufacturing sites has the
largest OT footprint, and where is unpatched CVE
exposure concentrated regionally?"). H3 hexbin
renders each region as a discrete clickable hexagon
with a deterministic per-cell asset count, so the
operator can rank regions visually and click any
hot hex to see the contributing site names + asset
inventories in a drilldown panel. The right layer
for **plant-leadership monthly review dashboards**
where the audience needs site-density ranking and
regional CVE-exposure pressure, NOT for per-asset
investigation (markers).

**markers vs H3 hexbin — when to choose which.**

- Use **markers** when the question is "show me each
  OT asset individually" (OT-asset-team
  investigation, vendor patch coordination). Per
  [cyber-vision/markers](./markers.md).
- Use **H3 hexbin** when the question is "which
  REGIONS / SITES have the largest OT footprint
  and where is CVE exposure concentrated?"
  (plant-leadership review, multi-site
  consolidation planning). This recipe.

Both layers can coexist on the same dashboard via
the BM-CT-1 layer contract — operators toggle
between site-level density and per-asset detail
without re-running the underlying search.

**Typical sourcetype / index:** `index=cybervision`
sourcetype-prefixed as `cisco:cybervision:*`. The
TA is `TA-cisco-cybervision`. The site lookup
(`cybervision_sites.csv`) is operator-maintained,
no defaults shipped — same contract as the markers
companion. See §6 Gotchas for the schema.

## 2. SPL recipe

```spl
index=cybervision sourcetype="cisco:cybervision:components" earliest=-24h latest=now
| dedup asset_id sortby - _time
| rename asset_id AS id
| join type=left id [
    search index=cybervision sourcetype="cisco:cybervision:vulnerabilities" earliest=-24h latest=now
    | stats max(cvss_score) AS max_cvss, dc(cve_id) AS cve_count BY asset_id
    | rename asset_id AS id
  ]
| fillnull value=0 max_cvss cve_count
| lookup cybervision_sites.csv asset_id AS id OUTPUT lat, lon, zone_purdue_level, safety_related, site_name
| where isnotnull(lat) AND isnotnull(lon)
| eval max_cvss=round(max_cvss, 1)
| eval value=1
| fields id, lat, lon, value, max_cvss, cve_count, zone_purdue_level, safety_related, site_name
| sort - max_cvss, id
| head 5000
```

Why this exact shape, line by line:

- **`index=cybervision
  sourcetype="cisco:cybervision:components"
  earliest=-24h latest=now`** — components stream
  over 24 h, identical to the markers companion.
  Cyber Vision Center re-publishes the asset
  inventory periodically (default every 5 min for
  changed records); 24 h guarantees every active
  asset is in the sample.
- **`dedup asset_id sortby - _time`** — one row per
  asset (the freshest record). Same dedup as the
  markers companion — Cyber Vision re-publishes
  the entire asset record on changes; the freshest
  row carries the current state.
- **`rename asset_id AS id`** — adopt Better Map's
  canonical `id` alias up front.
- **`join` subsearch (vulnerabilities)** — count
  CVEs per asset and pick the worst CVSS. Bounded
  to the same 24 h window. `max(cvss_score)` and
  `dc(cve_id)` carry through to the popup so the
  operator can disambiguate "one critical CVE" vs
  "dozens of medium CVEs" per cell. Same subsearch
  shape as the markers companion (no events join
  in this recipe — at the regional aggregation
  level, per-asset event noise is less interesting
  than per-asset CVE exposure).
- **`fillnull value=0 max_cvss cve_count`** —
  assets with no CVEs get NULL from the join;
  promote NULL to 0 so the popup reads "0 CVEs"
  instead of blanks.
- **`lookup cybervision_sites.csv asset_id AS id
  OUTPUT lat, lon, zone_purdue_level,
  safety_related, site_name`** — THE critical line,
  identical to the markers companion. The site
  lookup is operator-maintained (no defaults
  shipped); the contract is documented in §6
  Gotchas. `zone_purdue_level` and
  `safety_related` are the OT-safety annotations
  per
  [`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
  Rule 5 — read-only mirrored from the customer's
  Safety Requirements Specification.
- **`where isnotnull(lat) AND isnotnull(lon)`** —
  drop assets without site registration. Same
  defensive filter as the markers companion.
- **`eval max_cvss=round(max_cvss, 1)`** — round
  to one decimal for display.
- **`| eval value=1`** — **the H3 hexbin
  contract**. Every asset row contributes a value
  of 1; with `hexbinAggregate: "sum"` the cell
  colour becomes the count of OT assets in that
  region — the asset-density metric the recipe is
  optimised for. To change the optimisation target,
  swap to `| eval value=max_cvss` for
  CVE-pressure-by-region (the cell colour reads
  as worst-CVSS-per-cell with `hexbinAggregate:
  "max"`, or sum-of-worst-CVSS-per-cell with
  `"sum"`) — both are valid design choices, see §4
  for the trade-offs.
- **`| head 5000`** — render budget. The H3 hexbin
  layer collapses 5000 assets into at most a few
  hundred visible hex cells at resolution 3 (a
  typical multi-site OT install carries
  500-2000 assets per site across 10-30 sites).
  Bump to 10000 for global enterprise deployments
  with hundreds of sites.

Every `|` starts its own physical line per the SPL
pipe-per-line contract in `splunk-conf-and-spl.mdc`.

## 4. Recommended formatter config

```json
{
  "pointRenderer": "h3",
  "hexbinAggregate": "sum",
  "hexbinResolution": 4,
  "hexbinOpacity": 0.7
}
```

Why this specific config:

- **`pointRenderer: "h3"`** — explicit pin to the
  H3 hexbin renderer. The `auto` renderer never
  picks H3; must be set explicitly.
- **`hexbinAggregate: "sum"`** — combined with
  `value=1` from the SPL, this produces **the asset
  count per cell** as the cell colour intensity.
  The cell reads as "how many OT assets are
  registered in this region?" — the canonical
  plant-density question. Alternative: switch the
  SPL to `eval value=max_cvss` and the aggregate
  to `"max"` for a "worst CVSS per cell" exposure
  view (useful for vulnerability-management
  triage panels).
- **`hexbinResolution: 4`** — **resolution 4** =
  ~17 km edge length per cell. **Different default
  from the cim-* H3 siblings (which use res 3 / ~120
  km).** OT assets cluster much more tightly than
  internet-source-IP populations — an entire
  manufacturing site at "Houston, TX" sits inside a
  ~1-2 km radius, and even multi-site clusters
  (e.g. Houston East + Houston West + Houston
  Refinery) sit inside a ~30 km radius. Resolution
  4 keeps each site as its own hex cell at world
  zoom rather than merging into a "Texas" mega-hex
  (which is what res 3 would do). For continent-
  zoom panels showing inter-site distribution,
  res 3 is appropriate; for per-site panels,
  raise to res 5 (~6 km cells) or res 6 (~3 km
  cells).
- **`hexbinOpacity: 0.7`** — visually consistent
  with the cim-* H3 siblings. Hex cells over
  industrial geography (port complexes,
  refinery zones, manufacturing parks) benefit
  from the basemap showing through enough to
  contextualise where each site sits.
- **`value` is the H3-layer-required aggregation
  field.** Better Map's `dataFitness.js`
  auto-picks `value` by name. The SPL above
  already names the aggregation column `value`;
  no further formatter config needed.

## 6. Gotchas

- **OT safety — passive DPI is the REFERENCE
  DESIGN.** Same as the markers companion. Cyber
  Vision is explicitly named in
  [`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
  Rule 1 as the reference design for passive OT
  collection. This recipe consumes Cyber Vision's
  already-passive metadata stream — it does NOT
  itself probe the OT zone in any way.
- **OT safety — every asset row is read-only
  mirrored from the customer SRS.** Per Rule 5,
  the `safety_related` column in
  `cybervision_sites.csv` is a copy of the
  customer-supplied SIS-asset register, NEVER
  authored by VISTA. If the Safety Annex (per
  the OT-safety gate) is missing for any
  `safety_related=Y` row, STOP and get the
  customer's OT engineering team to author the
  SRS first.
- **OT safety — never disable / suppress / filter a
  Cyber Vision asset.** Per Rule 2, even if the
  hex aggregation collapses noisy assets into a
  cell count, do NOT drop assets at the
  props/transforms layer — drop at the PANEL layer
  only (`NOT safety_related="true"` for an
  OT-non-safety overview panel), and record the
  panel-level filtering decision in the Built
  Content Catalog with OT engineering approval.
- **OT safety — SOAR action scope.** Per Rule 3,
  any SOAR playbook triggered by THIS panel (e.g.
  "high-CVSS-density region → notify regional OT
  manager") must keep its containment actions in
  the IT zone. Notify the OT operator; do NOT
  auto-issue any command to the assets in the
  cell.
- **`cybervision_sites.csv` schema (REQUIRED).**
  Same operator-maintained CSV lookup as the
  markers companion — see
  [cyber-vision/markers § 6 Gotchas](./markers.md#6-gotchas)
  for the full schema. Recap: required columns
  are `asset_id`, `lat`, `lon`,
  `zone_purdue_level`, `safety_related`; optional
  `site_name`.
- **Resolution choice MATTERS.** OT asset
  populations cluster at site-scale (~1-2 km
  radius per facility). Resolution 3 (~120 km
  cells) MERGES multi-site regional clusters
  into a single mega-hex — useful for "show me
  every site in the Gulf Coast" but useless for
  "show me each Houston-area site as its own
  cell." Resolution 4 (~17 km) is the recommended
  default for typical multi-site OT
  deployments. Resolution 5 (~6 km) gives
  per-site granularity within a metro. Resolution
  6 (~3 km) gives per-building granularity within
  a large industrial complex (e.g. an oil
  refinery with multiple process units). Match
  to the dashboard zoom and the operator's
  expected pan-zoom behaviour.
- **Aggregate function semantics.** With
  `value=1`, `sum` produces asset count per cell
  (recommended default — answers "where are the
  most OT assets?"). With `value=max_cvss`, `max`
  produces the worst CVSS per cell (answers
  "where is our exposed surface?"), `avg`
  produces the mean CVSS per cell (answers "where
  is the most uniformly-exposed site?"). The two
  optimisation targets answer different questions
  — author BOTH as separate panels in a CVE
  triage dashboard if needed.
- **`asset_id` cardinality drift.** Same caveat
  as the markers companion. Cyber Vision
  sometimes re-issues `asset_id` after a sensor
  restart (rare, but documented). Cross-check
  with `asset_mac` if drift is suspected — MAC
  addresses are stable across sensor restarts.
- **CVSS join cardinality.** Same caveat as the
  markers companion. A single asset can carry
  many CVEs; `max(cvss_score)` surfaces the
  worst per asset, `dc(cve_id)` carries the
  count to the popup so the operator can
  distinguish "one critical CVE" from "dozens
  of medium CVEs". At the H3 cell level, both
  aggregates carry through as
  `max(max_cvss)` (the worst single asset's
  worst CVE in the cell) and
  `sum(cve_count)` (the total CVE count across
  all assets in the cell) — both surface in the
  popup.
- **Time range.** Hard-coded `earliest=-24h
  latest=now`. Cyber Vision's components stream
  re-publishes only on change; 24 h covers
  slow-changing inventory. Avoid narrowing
  below 1 h (assets that haven't re-published in
  the window drop off the map).
- **PII / GDPR posture.** Same as the markers
  companion. Asset names embed plant-floor
  semantics (`PLC-FLOOR3-PAINT-A02`) —
  REGULATED in some jurisdictions. The H3
  hexbin panel is generally LOWER-risk than the
  markers companion because the cell aggregate
  collapses individual asset names into a
  regional count, but the popup may still
  expose asset-name-level data when the
  operator drills into a cell. Per ROADMAP §1a,
  Better Map never sends event data outside
  `splunkd:8089`. Restrict via Splunk RBAC on
  the `cybervision` index for audiences
  without "see OT asset naming" authorisation.

3. Run the recipe SPL at resolution 4 (the
   recommended default) and confirm at least one
   hex cell renders per known site.

   companion side by side — the cell with the
   highest count at world zoom should
   correspond to the densest marker cluster.
5. Cross-check `safety_related` column values
   against the customer's Safety Requirements
   Specification — discrepancies must be
   resolved with OT engineering BEFORE the
   panel goes into a customer dashboard.
6. If experimenting with the CVE-exposure
   alternative (swap `value=1` for
   `value=max_cvss` and aggregate `max`), run
   side-by-side with the asset-density view to
   confirm the cell hot-spots shift to the
   sites with the worst unpatched assets.
7. Update the frontmatter to `status: verified`,
   fill in `verified_against` (include
   `splunk_app: "TA-cisco-cybervision"` and a
   non-PII tenant identifier), and submit a
   follow-up PR.
