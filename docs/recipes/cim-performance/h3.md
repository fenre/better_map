# CIM Performance — H3 hexbin

The geographic-aggregation complement to the
[cim-performance/markers](./markers.md) recipe — same CIM-
accelerated `Performance.CPU` and `Performance.Memory`
datasets, same ES Asset & Identity asset lookup for
hostname → lat / lon, but rendered as H3 hexagonal cells
rather than discrete markers. The H3 layer surfaces
**per-region infrastructure load PRESSURE** as hex cell
colour intensity: hot hexes indicate datacenters /
availability zones with the highest aggregate CPU/memory
load; cool hexes indicate quiet regions. This is the
natural shape when the dashboard question is "which
geographic region's infrastructure is hottest right now?"
rather than "which individual host should I investigate?".

## 1. Source description

Same Splunk **Performance** Common Information Model (CIM)
data model as the companion [markers](./markers.md) recipe
— vendor-agnostic, normalising telemetry from Universal
Forwarders, Splunk Infrastructure Monitoring, Cisco
Catalyst Center, AWS CloudWatch, Azure Monitor, GCP
Stackdriver, and every TA tagged
`performance,cpu`/`performance,memory`/etc.

**Why H3 hexbin for CIM Performance.** A markers view at
world zoom collapses dense datacenter clusters (one AWS
`us-east-1` availability zone hosts 100s of monitored
hosts in your fleet; one Azure `eastus2` region might host
1000s for a heavy-cloud customer) into overlapping circles
that hide individual host CPU values under visual
clutter. An H3 hexbin AGGREGATES the underlying hosts
into regular hexagonal cells (Uber's
[H3 spatial index](https://h3geo.org/) — equal-area,
equal-shape, with predictable cell sizes per resolution
level), and colours each cell by an aggregate function
(mean / max / sum) of the per-host values. The result
reads as "infrastructure pressure per region" — perfect
for **SRE leadership capacity dashboards** and **cloud-
cost optimisation reviews** where the question is "which
region's fleet is running hottest?", NOT for per-host
investigation (use markers for that).

**Heatmap vs H3 hexbin — when to choose which.**
- Use **heatmap** when the panel question is "where is
  the pressure SMOOTHLY distributed?" (Gaussian blob,
  blurry edges, good for "show me general pressure")
- Use **H3 hexbin** when the panel question is "which
  REGION/CELL is hottest?" (discrete cells, sharp
  edges, good for "show me per-region rankings,
  count cells in a region, click a cell to drilldown")
- H3 hexbin allows aggregate functions OTHER than count
  (mean / max / sum) on a per-row VALUE field; heatmap
  is fundamentally a per-feature-density renderer with
  optional weight.
- For "infrastructure performance per datacenter," H3
  hexbin is usually the right choice because the
  operator wants to know "what's the avg CPU in
  `us-east-1` vs `us-west-2`?" — a question heatmap
  cannot answer directly.

**Typical sourcetype / index:** any sourcetype tagged
`performance,cpu` and `performance,memory` — the model
is accelerated for production tenants. The TA app context
required is `Splunk_SA_CIM`. The asset lookup is
operator-maintained (this recipe uses the same
`asset_lookup_by_str` from the ES A&I framework as the
markers companion).

## 2. SPL recipe

```spl
| tstats summariesonly=true latest(Performance.cpu_load_percent) AS cpu_load_percent FROM datamodel=Performance.CPU WHERE earliest=-15m latest=now BY Performance.dest
| rename Performance.dest AS dest
| append [
    | tstats summariesonly=true latest(Performance.mem_used_percent) AS mem_used_percent FROM datamodel=Performance.Memory WHERE earliest=-15m latest=now BY Performance.dest
    | rename Performance.dest AS dest
  ]
| stats latest(cpu_load_percent) AS cpu_load_percent, latest(mem_used_percent) AS mem_used_percent BY dest
| where isnotnull(cpu_load_percent)
| lookup asset_lookup_by_str src AS dest OUTPUT lat AS lat, long AS lon
| where isnotnull(lat) AND isnotnull(lon)
| eval cpu_load_percent=round(cpu_load_percent, 1)
| eval mem_used_percent=round(coalesce(mem_used_percent, 0), 1)
| eval value=cpu_load_percent
| eval id=dest
| fields id, lat, lon, value, cpu_load_percent, mem_used_percent
| sort - value
| head 10000
```

Why this exact shape, line by line:

- **Two `tstats summariesonly=true` against
  `datamodel=Performance.CPU` / `.Memory`** — same pattern
  as the markers recipe but limited to CPU and Memory
  (the H3 hexbin recipe drops Storage because storage
  pressure is typically PERSISTENT per host and doesn't
  vary across a datacenter on a 15 min cadence — it
  would mute the cell-to-cell variance the hexbin layer
  is designed to surface). For a tenant where storage
  IS the SRE concern, swap `Performance.CPU` for
  `Performance.Storage` and `cpu_load_percent` for
  `storage_used_percent`. The markers recipe ships all
  three because it answers "which HOSTS are in trouble";
  this recipe specialises on the per-region CPU question.
- **`append` + `stats latest(...) BY dest`** — same
  multi-dataset merge pattern as the markers recipe.
  Avoids `join`'s 50K row × 60 s truncation per the SPL
  quality rules.
- **`where isnotnull(cpu_load_percent)`** — the H3
  hexbin layer needs a non-null `value` per row to
  compute the cell aggregate. Hosts with memory-only
  telemetry (no CPU TA installed) are dropped from this
  panel; surface them in a companion table for the
  operator to backfill the CPU collection. `mem_used_percent`
  is allowed to be null (handled with `coalesce(..., 0)`
  below for popup display only — does NOT drive the
  hex colouring).
- **`lookup asset_lookup_by_str src AS dest OUTPUT lat
  AS lat, long AS lon`** — same ES A&I asset lookup as
  the markers recipe. See the markers companion
  Gotchas section for the three substitution patterns
  (ITSI entity collection, DNS-or-CMDB CSV, geocode-
  by-DNS) for tenants without ES.
- **`where isnotnull(lat) AND isnotnull(lon)`** — drop
  hosts with no geographic attribution. Real
  performance values without geographic representation
  are surfaced in a companion table panel.
- **`eval cpu_load_percent=round(cpu_load_percent, 1)`**
  — round for display (the underlying value is float-
  precise from the raw telemetry).
- **`eval mem_used_percent=round(coalesce(mem_used_percent,
  0), 1)`** — `coalesce` defends against the
  CPU-only-host case (a host with CPU telemetry but no
  Memory telemetry would otherwise produce
  `mem_used_percent=null` which renders as "null" in
  the popup; `0` is a clearer sentinel for "no data").
- **`eval value=cpu_load_percent`** — **the H3 hexbin
  contract**. The layer expects a `value` field per
  row that it can aggregate across rows in the same
  cell (using whichever aggregate function the
  formatter's `hexbinAggregate` option picks). Setting
  `value` from CPU makes the hexbin colour represent
  "average CPU pressure in this region" (per the §4
  formatter config). To make the colour represent
  memory pressure, swap `eval value=mem_used_percent`.
  To represent worst-of-both, swap
  `eval value=max(cpu_load_percent, mem_used_percent)`
  but note this creates a hexbin showing "worst-case
  pressure regardless of which signal," which is
  harder to interpret than a pure CPU or pure memory
  panel.
- **`eval id=dest`** — adopt Better Map's `id` alias.
  Same as the markers recipe.
- **`fields ...`** — explicit field list, includes
  `cpu_load_percent` and `mem_used_percent` for popup
  display when the operator clicks into a hex cell.
- **`sort - value`** — highest-pressure hosts first.
  Combined with `head 10000` this gives the hexbin
  layer all the heavy-load hosts even when the long-
  tail is truncated. (`head 10000` is generous — the
  hexbin layer aggregates many hosts per cell, so
  even 10000 hosts collapse to ~50-200 visible cells
  at typical world-zoom + resolution 3.)
- **`head 10000`** — render budget. CIM Performance
  monitors entire fleets (10s of thousands of hosts
  for large customers). 10000 covers every typical
  enterprise fleet; per-cell aggregation reduces the
  rendered geometry count to manageable levels even
  for the largest tenants.

Note every `|` starts its own physical line per the SPL
pipe-per-line contract.

## 4. Recommended formatter config

```json
{
  "pointRenderer": "h3",
  "hexbinAggregate": "avg",
  "hexbinResolution": 3,
  "hexbinOpacity": 0.7
}
```

Why this specific config:

- **`pointRenderer: "h3"`** — explicit pin to the H3
  hexbin renderer. The `auto` renderer never picks H3
  (it's a deliberate panel-design choice, not a fallback);
  must be set explicitly.
- **`hexbinAggregate: "avg"`** — **average CPU per
  cell** is the natural aggregation for a per-region
  load-pressure panel. The cell colour reads as "the
  avg CPU% of all monitored hosts in this hex," which
  is exactly what an SRE capacity-planning conversation
  wants ("our `us-east-1` fleet is averaging 78 % CPU
  this week, vs `eu-west-1` at 42 %"). Other valid
  aggregates per
  [`docs/_machine/formatter-schema.json`](https://github.com/fenre/better_map/blob/main/docs/_machine/formatter-schema.json):
  `sum` (total CPU% across cell — meaningless physically
  but useful for "fleet size + CPU pressure" combined
  signal), `max` (worst host in the cell — useful for
  "is anything in this region in trouble?"), `min`
  (lightest-loaded host — useful for "where is there
  spare capacity?"), `count` (just host density — but
  if that's the question, use `cim-performance/markers`
  with a cluster renderer instead).
- **`hexbinResolution: 3`** — **resolution 3** = ~120 km
  edge length per cell. Per the
  [H3 resolution table](https://h3geo.org/docs/core-library/restable),
  resolution 3 cells comfortably contain entire metro
  areas (Greater London, Greater New York, Greater
  Tokyo) and are typically the right granularity for a
  world-zoom panel showing "datacenters per region."
  At resolution 3 the global hex count is ~41k —
  modest render load. For continent-zoom panels (e.g.
  "show me only North American datacenter pressure"),
  raise to 4 (~17 km cells, finer resolution within a
  continent). For per-state / per-province views, raise
  to 5 (~6 km cells). For metro-zoom investigation,
  raise to 6 (~2 km cells — each AWS availability zone
  gets its own cell).
- **`hexbinOpacity: 0.7`** — same opacity as the
  splunk-stream/heat recipe. The H3 hexbin layer
  benefits slightly less from low opacity than the
  heat layer because hexes have sharp edges (basemap
  city labels showing THROUGH a hex are less of an
  issue than showing through a Gaussian heat blob),
  but `0.7` keeps the panel visually consistent across
  layer types in mixed-layer dashboards. Raise to
  `0.85-0.9` for an isolated H3-only panel where the
  basemap underlay matters less.
- **`value` is the H3-layer-required aggregation
  field.** Better Map's `dataFitness.js` auto-picks
  `value` by name (per the same convention as `weight`
  for heatmap, `bytes_out` for choropleth, etc.). The
  SPL above already names the aggregation column
  `value`; no further formatter config needed. If you
  rename the column in SPL, set the formatter's
  `valueField` option (or whichever name the formatter
  schema uses — check
  [`docs/_machine/formatter-schema.json`](https://github.com/fenre/better_map/blob/main/docs/_machine/formatter-schema.json)).

## 6. Gotchas

- **Acceleration is mandatory for `summariesonly=true`.**
  Same as the markers recipe — if your tenant's CIM
  Performance data model is not accelerated, the
  `tstats summariesonly=true` query returns zero rows.
  Two fixes: (a) enable acceleration (5 min span,
  6-week retention — the splunk-datamodels-conf skill
  defaults work); or (b) drop `summariesonly=true` and
  pay the raw-event query cost.
- **H3 hexbin vs heatmap — when to choose which.**
  Both are aggregate-density layers; the difference is:
  H3 has sharp hexagonal cells with a deterministic
  per-cell aggregate function and a clickable drilldown
  affordance per cell; heatmap has smooth Gaussian
  blobs with a continuous weight field and no per-blob
  drilldown. The H3 hexbin is the right layer for
  "which region is hottest" questions where the panel
  user wants to CLICK into a region. The heatmap is the
  right layer for "show me pressure smoothly distributed"
  questions where the panel user wants a visual gestalt
  but not per-region drilldown. For CIM Performance
  specifically: H3 wins for SRE / capacity-planning
  panels (operator drills into one cell to see the
  list of hosts contributing); heatmap wins for
  executive briefings (smooth gradient reads cleaner
  in a slide deck). Both can coexist via the BM-CT-1
  layer contract.
- **H3 cell SAMPLE SIZE matters.** A hex cell with
  ONE host inside it shows that one host's CPU% as the
  cell's "average" — misleading at world zoom (one
  outlier in a sparse region paints a whole cell red).
  Add a `where` filter to drop cells with insufficient
  sample size if your tenant has sparse regions. The
  H3 layer does not currently expose a per-cell-count
  threshold formatter option; the easiest workaround
  is a SPL pre-aggregation:
  `| stats avg(cpu_load_percent) AS avg_cpu, count AS
  host_count BY <h3_index_for_resolution_3>` then
  `| where host_count >= 3` before the panel
  visualisation. This requires using the `h3` Splunk
  command (ships with Splunk 9.0+ via the
  `splunkbase:h3` app) or pre-computing the H3 index
  in SPL via
  `| eval h3_idx=md5(lat."_".round(lon,0))` (NOT a
  real H3 index — just a placeholder for the workaround
  pattern; replace with the actual H3 lat/lon→cell
  function once `splunkbase:h3` is in your tenant).
- **Aggregate function semantics.** `avg` averages all
  host CPU% in the cell — sensitive to outliers.
  `sum` is meaningless for percentage values (summing
  500 hosts' CPU% gives "1000 % CPU" which only makes
  sense as a relative-load proxy). `max` highlights
  the worst host per cell — clearer signal for
  incident detection but loses the "is this a fleet
  problem or a single-host problem" distinction. `count`
  reduces to host-density which the markers/cluster
  recipe already shows. Pick `avg` for capacity
  reviews; `max` for incident war rooms; never `sum`
  for percentage values.
- **`asset_lookup_by_str` requires ES — same as
  markers recipe.** See [cim-performance/markers](./markers.md)
  §6 for the three substitution patterns (ITSI entity
  collection, DNS-or-CMDB CSV, geocode-by-DNS).
- **Time range.** Hard-coded `earliest=-15m latest=now`.
  Same rationale as the markers recipe (5 min accel
  span × 3 covers one missed sample). For "capacity
  trend over the workday," widen to `-8h` and switch
  `latest()` to `avg()` so the cell colour represents
  "avg CPU% over the last 8 h" rather than "freshest
  sample CPU%."
- **PII / GDPR posture — same as markers recipe.**
  Hostnames may embed regulated information; restrict
  via Splunk RBAC on the CIM Performance indexes for
  audiences without "see infrastructure naming" auth.
  Per ROADMAP §1a, Better Map never sends event data
  outside `splunkd:8089`.
- **No OT safety dependency.** Same as markers recipe
  — this recipe is pure IT infrastructure performance.
  If your CIM Performance model also ingests OT-zone
  equipment (PLC CPU, HMI memory), filter those hosts
  OUT here (`NOT dest IN ("plc-*", "hmi-*", "rtu-*")`)
  and put them in a SEPARATE recipe with
  `ot_safety_relevant: true` per
  [`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
  Rule 6 — a CPU-bound PLC and a CPU-bound web server
  need fundamentally different operator responses and
  should not visually compete on the same map.

dispatched against a tenant with CIM Performance
accelerated AND an A&I lookup carrying multi-region
lat/long. A maintainer with REST auth to such a tenant
should:

1. Confirm Performance is accelerated:
   `| datamodel Performance | head 1`.
2. Confirm the A&I lookup carries lat/long across
   MULTIPLE regions (the hexbin only works if there's
   geographic variance):
   `| inputlookup asset_lookup_by_str | where
   isnotnull(lat) | stats dc(lat) AS distinct_lats`.
3. Run the recipe SPL and confirm the panel renders
   at least 3 distinct hex cells with meaningful
   `value` variance.
4. Verify per-cell drilldown works: click into a hex
   to see the list of contributing hosts.
5. Tune `hexbinResolution` to match the panel's zoom
   level (3 for world, 4 for continent, 5 for state,
   6 for metro — see §4).
6. Update the frontmatter to `status: verified`, fill
   in `verified_against` (include `splunk_app:
   "Splunk_SA_CIM"`), and submit a follow-up PR.
