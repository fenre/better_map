# OT Datastreamer / Edge Hub — H3 hexbin

The discrete-cell regional complement to the
[ot-datastreamer/markers](./markers.md) and
[ot-datastreamer/heat](./heat.md) recipes — same
`edge_hub_*` index union, same operator-maintained
`edge_hub_sites.csv` lookup for physical lat / lon and
Purdue / safety annotation, but rendered as
**continental H3 hexbins** rather than per-appliance pins
or per-site smooth heat blobs. The h3 layer surfaces
**OT telemetry VOLUME as discrete hexagonal cells** that
aggregate every site falling within their geographic
bounds — natural for regional capacity briefings ("how
much OT data lands in EMEA vs APAC vs NAMER?"), board-
level scope-of-deployment maps ("which continents already
host Edge Hub fleets?"), and licensing / data-residency
audits ("is any OT telemetry crossing the Asian-region
boundary we contracted for?"). Distinct from the heat
companion (which renders smooth per-site blobs without
hard borders) and the markers companion (which renders
per-appliance pins with liveness colouring).

**OT safety boundary (this recipe is `ot_safety_relevant:
true`).** Like the companion markers and heat recipes,
this panel rests on the
[`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
contract: passive collection only, SIS-related signals
read-only, no write-back to Level-0/1/2 zones, no SOAR
actions wired to a Level-0/1/2 target. The hexbin form is
**REGIONALLY AGGREGATED** (one hex covers thousands of km²
at typical world-zoom + resolution 3) but EVERY rule still
applies — and the regional aggregation makes safety-flag
handling MORE delicate, not less (see §6 Gotchas — a hex
showing `site_has_safety_hub=1` means at least ONE site
in that hex carries SIS-relevant telemetry; the popup MUST
NOT imply every site in the hex does).

## 1. Source description

Same Splunk **Edge Hub / OTI Datastreamer** event union as
the companion [markers](./markers.md) and [heat](./heat.md)
recipes — the OR of every `edge_hub_*` index plus the
optional `bms` index, joined against the operator-
maintained `edge_hub_sites.csv` lookup for physical lat /
lon + Purdue level + safety classification.

**Why h3 hexbin for OT telemetry.** Markers answer
"which APPLIANCE is silent?" (per-hub investigation).
Heat answers "which SITE is hottest?" (per-site pressure
gradient). H3 hexbin answers "which REGION is generating
the most OT telemetry, with hard partition borders so I
can drill INTO a region?" — the right shape for **OT
capacity-planning regional briefings**, **board-level
deployment-scope maps**, and **data-residency audits**.
The hard hexagonal partition is the key visual cue: a
region executive can SEE the discrete boundary between
EMEA and APAC, and click a hex to drill into the
site-level detail that the heat layer renders smoothly.

For per-region performance KPIs (e.g. "average Edge Hub
event rate per hex"), this recipe's hexbin-aggregate-sum
gives total volume; swap to `hexbinAggregate: "avg"` for
per-site averages and `hexbinAggregate: "max"` for
worst-case hex spotting (the busiest single site in each
region).

**Typical sourcetype / index:** anything matching
`edge_hub_*` plus the `bms` index. The TA is
`Splunk_TA_oti`. The site lookup is operator-maintained
(see [ot-datastreamer/markers](./markers.md) §6 for the
canonical `edge_hub_sites.csv` schema).

## 2. SPL recipe

```spl
index=edge_hub_* OR index=bms earliest=-1h latest=now
| stats count AS event_count BY host
| lookup edge_hub_sites.csv host OUTPUT lat, lon, hub_name, site_id, zone_purdue_level, safety_related
| where isnotnull(lat) AND isnotnull(lon)
| stats sum(event_count) AS event_count, values(zone_purdue_level) AS purdue_levels, max(safety_related) AS site_has_safety_hub BY site_id, lat, lon
| eval value=event_count
| eval id=site_id
| fields id, lat, lon, site_id, event_count, value, purdue_levels, site_has_safety_hub
| sort - event_count
| head 5000
```

Why this exact shape, line by line:

- **`index=edge_hub_* OR index=bms earliest=-1h
  latest=now`** — same union and time window as the
  markers and heat companions. The 1 h window matches
  industrial telemetry cadences and gives the hexbin a
  meaningful pressure-of-recent-hour read; widen to
  `-24h` for daily-total regional volume, or to `-30d`
  with a summary-indexed roll-up (see §6 Gotchas) for
  monthly capacity reporting.
- **`stats count AS event_count BY host`** — first
  aggregation: one row per Edge Hub appliance, with the
  raw event count. Identical to the heat recipe's first
  `stats` aggregation.
- **`lookup edge_hub_sites.csv host OUTPUT lat, lon,
  hub_name, site_id, zone_purdue_level, safety_related`**
  — same operator-maintained site lookup as the
  companions. Returns the per-hub physical lat/lon,
  human-readable hub name, operator-defined site
  grouping, Purdue level classification, and safety-
  related boolean. Per
  [`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
  Rule 5, the `safety_related` column is read-only
  mirrored from the customer's Safety Requirements
  Specification (SRS) — never authored by Splunk or
  Better Map.
- **`where isnotnull(lat) AND isnotnull(lon)`** — drop
  hubs without recorded physical location. Real
  transmitting hubs without lat/lon should be surfaced
  in a companion table panel for operator backfill
  (same pattern as the markers / heat recipes).
- **`stats sum(event_count) AS event_count, values(...)
  AS purdue_levels, max(safety_related) AS
  site_has_safety_hub BY site_id, lat, lon`** —
  collapses the per-hub rows to ONE row per site. The
  hexbin layer's per-cell aggregation will then collapse
  the per-site rows further into per-hex aggregates.
  `values(zone_purdue_level)` collects the set of
  Purdue levels active at the site (popup metadata).
  `max(safety_related)` (treating `true=1, false=0`) is
  a boolean OR — `1` if ANY hub at the site carries a
  safety-related signal, else `0`. This is critical for
  §6 Gotchas: the hexbin popup MUST carry the safety
  annotation per Rule 6, and the operator MUST
  understand that a hex showing
  `site_has_safety_hub=1` means at least ONE site in
  the hex carries SIS-relevant telemetry (NOT that
  every site in the hex does).
- **`eval value=event_count`** — **the H3 hexbin
  contract**. The layer expects a `value` field per row
  that it aggregates across rows in the same cell via
  whichever aggregate function the formatter's
  `hexbinAggregate` option picks. Setting `value` from
  the per-site `event_count` makes the hexbin colour
  represent "total telemetry volume in this region"
  when `hexbinAggregate: "sum"` (the §4 default). For
  per-site averages within each region, swap to
  `hexbinAggregate: "avg"`; for worst-case-site
  spotting, swap to `hexbinAggregate: "max"`.
- **`eval id=site_id`** — adopt Better Map's `id`
  alias. `site_id` is the natural identifier for a
  per-site row; the hexbin layer's per-cell
  aggregation does not require unique `id` values
  (multiple sites can share a hex).
- **`fields ...`** — explicit field list, includes
  `event_count`, `purdue_levels`, and
  `site_has_safety_hub` for popup display when the
  operator clicks into a hex cell. The popup will
  show per-site detail for every site that contributed
  to the hex aggregate.
- **`sort - event_count`** — busiest sites first;
  combined with `head 5000` this gives the hexbin all
  heavy-load sites even when the long-tail is
  truncated. (`head 5000` is heavily defensive — the
  largest multi-national OT operators run ~200 sites
  globally; 5000 is 25× the largest known fleet.)
- **`head 5000`** — render budget. Per-cell hex
  aggregation collapses thousands of sites into
  ~10-50 visible hexes at world-zoom + resolution 3,
  so even at the truncation limit the rendered
  geometry count stays low.

Note every `|` starts its own physical line per the SPL
pipe-per-line contract.

## 4. Recommended formatter config

```json
{
  "pointRenderer": "h3",
  "hexbinAggregate": "sum",
  "hexbinResolution": 3,
  "hexbinOpacity": 0.7
}
```

Why this specific config:

- **`pointRenderer: "h3"`** — explicit pin to the H3
  hexbin renderer. The `auto` renderer chooses a
  layer based on feature count; for OT capacity panels
  the hexbin is the intended shape regardless of the
  number of sites in scope.
- **`hexbinAggregate: "sum"`** — sums every site's
  `value` (`event_count`) within each hex cell. The
  right default for **regional capacity briefings**
  (the per-hex value reads as "total OT telemetry
  volume in this region"). For per-site averages
  within each region, swap to `"avg"`; for worst-case
  spotting, swap to `"max"`.
- **`hexbinResolution: 3`** — **continental scope**.
  H3 resolution 3 produces hexes of ~12,500 km² edge-
  length at world zoom — roughly the size of a US
  state or a small European country. This is the
  right zoom for **board-level regional briefings**
  (EMEA vs APAC vs NAMER comparisons) and **data-
  residency audits** (one hex maps roughly to one
  country-scale regulatory jurisdiction). For
  national-scope drilldowns (e.g. "show me only US
  hubs broken down by state"), bump to resolution 4
  (~1,800 km² edge-length, ~US-state-sized). For
  per-site drilldowns, switch to the heat or markers
  companions — hexbin is the WRONG layer below
  resolution 5.
- **`hexbinOpacity: 0.7`** — same opacity as the
  cim-performance/h3 recipe. At 1.0 the hexes fully
  occlude the basemap labels; at 0.5 too washed out
  for low-zoom regional reads; 0.7 is the sweet spot
  for region names (continents, country borders) to
  survive the hexagonal overlay.
- **`value` field drives hex colouring automatically.**
  Same as every h3 recipe — `dataFitness.js` auto-
  picks the `value` field by name.

## 6. Gotchas

- **OT safety — hexbin MUST preserve the safety
  annotation BUT NOT imply uniform safety status across
  the hex.** Per
  [`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
  Rule 6, every detection / panel that depends on a
  safety-related signal MUST carry the safety-dependent
  metadata. The SPL above does this via
  `max(safety_related) AS site_has_safety_hub` — a hex
  containing ANY safety-relevant site will surface
  `site_has_safety_hub=1` in the popup. Dashboards
  rendering this hexbin MUST display the safety flag in
  the popup per-site (not just the hex-aggregate) so
  operators understand WHICH specific site in the hex
  carries SIS-relevant telemetry. NEVER strip the
  `safety_related` column from the lookup to "simplify"
  the panel — that violates Rule 2 (NEVER disable,
  suppress, or filter a safety-related signal). The
  hex-aggregate display is the regional read; the
  per-site popup is the SOC-ready compliance evidence.
- **OT safety — regional aggregation can MASK
  silent-safety-hub conditions.** A hex with 10 sites
  where 1 site (SIS-relevant) has gone silent will
  still show high `value` because the other 9 sites
  produce plenty of events. The hexbin gives NO visual
  cue for the silent safety hub. Pair this panel with
  a separate "silent safety hubs" alert per the
  `ot-datastreamer/heat` §6 Gotchas guidance — the
  alert covers the silent-detection that the visual
  layer cannot. The markers companion surfaces silent
  hubs more naturally (their
  `last_seen_minutes_ago` colour goes red); the h3
  hexbin does not, by design.
- **OT safety — passive collection ONLY.** Per Rule 1,
  every Edge Hub forwarding `safety_related=Y`
  signals MUST use a passive collection method. This
  recipe surfaces regional event volumes; the
  constraint is enforced at the `Splunk_TA_oti`
  collector / Edge Hub configuration layer, NOT at
  the SPL or visualization layer.
- **OT safety — SOAR scope ends at the IT / IT-OT
  DMZ.** Per Rule 3, any SOAR playbook triggered FROM
  this panel MUST stop at the IT zone. A "hot
  region" detected here might mean "the EMEA fleet is
  thrashing under operator workload" — that's an OT
  engineering decision, NOT a SOAR target. Surface to
  the regional OT operator's own ticketing / SCADA
  HMI; do not auto-act on Level-0/1/2 assets.
- **`edge_hub_sites.csv` schema — same as markers /
  heat recipes.** See [ot-datastreamer/markers](./markers.md)
  §6 for the canonical schema. The h3 recipe needs
  the same lookup with the additional `site_id` column
  populated (REQUIRED here, same as the heat recipe —
  the SPL aggregates `BY site_id, lat, lon`).
- **Resolution tuning gotcha.** Resolution 3 (the
  default) is right for continental briefings; bumping
  to resolution 5 (`~252 km²` edge-length) gives
  per-metro-area detail but typically over-decomposes
  OT site distributions (most regions have only a
  handful of sites; resolution 5 produces hexes that
  contain 0 or 1 sites and the panel looks sparse).
  For dense OT fleets (e.g. a single-country
  manufacturer with 50+ sites in one state), bump to
  resolution 4 (`~1,800 km²` edge-length). For
  ultra-dense facilities (one campus with multiple
  buildings each running an Edge Hub), this recipe
  is the wrong layer — switch to the markers
  companion for per-hub granularity.
- **Aggregate function semantics.** `hexbinAggregate:
  "sum"` is the default per §4 (regional VOLUME). For
  the question "which region has the most pressure
  PER SITE on average?", swap to `"avg"`. For the
  question "where is the single busiest site
  globally?", swap to `"max"`. NEVER swap to
  `"count"` — that would aggregate site COUNT per
  hex (which is just a "how many sites per region"
  panel and ignores the per-site `value` entirely).
- **Index naming drift — same as markers / heat
  recipes.** Some installs rename `edge_hub_*` to
  `oti_*` (older OTI Datastreamer versions) or
  `splunk_edge_*` (newer ones). Confirm with
  `| eventcount summarize=false index=* | search
  index=*edge* OR index=*oti*` and substitute the
  index wildcard in line 1.
- **Time range tuning.** The hard-coded 1 h window
  is right for **recent regional pressure briefings**.
  For monthly capacity reports (e.g. "show me total
  EMEA Edge Hub volume per month for the last
  quarter"), widen to `-90d` AND switch to a
  summary-indexed daily roll-up rather than raw
  `stats count` (the raw query at 90 d × ~200 sites
  × ~1M events/hr would cost serious search-head CPU
  and likely time out on busy tenants). The summary-
  index pattern is the same as the heat recipe's §6
  Gotchas guidance.
- **Data-residency audits.** This panel is one of
  the better tools for confirming "no OT telemetry
  crossed the EMEA / APAC boundary we contracted
  for". Run the panel filtered to a single region
  by `WHERE region IN ("EMEA")` on the
  `edge_hub_sites.csv` lookup (assumes the lookup
  carries a `region` column — operator-defined). A
  hex outside the expected region with non-zero
  `value` is the audit finding. Pair with an alert
  that fires on any per-hex `value > 0` outside the
  contracted region set.
- **PII / GDPR posture — same as markers / heat
  recipes.** Industrial telemetry is not PII, but
  site inventory data (site name, Purdue level,
  safety classification, region) CAN reveal
  sensitive customer architecture. Restrict via
  Splunk RBAC for regulated customers. Per ROADMAP
  §1a, Better Map never sends event data outside
  `splunkd:8089`.
