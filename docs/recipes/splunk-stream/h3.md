# Splunk Stream (wire data) — H3 hexbin

The per-region aggregation complement to the
[splunk-stream/markers](./markers.md) and
[splunk-stream/heat](./heat.md) recipes — same `stream:tls`
wire-data sourcetype, same `iplocation` geocoding of
destination IPs, but rendered as H3 hexagonal cells with
a per-cell aggregate function rather than discrete markers
or smooth heat blobs. The H3 layer surfaces **per-region
egress BYTE-VOLUME RANKINGS** as hex cell colour intensity
with deterministic per-cell aggregation: hot hexes indicate
geographic regions sending the most outbound bytes; cool
hexes indicate quiet regions. This is the natural shape for
**NetOps capacity-planning dashboards** and **data-residency
audit reviews** where the question is "WHICH GEOGRAPHIC
REGION is hottest by byte volume?" and the operator wants
to CLICK INTO a region to drill down to the contributing
destinations.

Completes the **splunk-stream source-row triplet** —
markers (wave 6), heat (wave 8), H3 hexbin (this wave) —
all three layers coexisting via the BM-CT-1 layer contract
on the same Dashboard Studio panel. This is the **9th
completed triplet** (joining cim-alerts, cim-authentication,
cim-network-traffic, cim-performance, cyber-vision, es-risk,
meraki, and netflow-sflow-ipfix). Combined with
cim-network-traffic and netflow-sflow-ipfix triplets, this
puts the **entire NetOps wire-data observability stack** in
full triplet coverage — wire-data, NetFlow, and CIM-normalised
traffic each have markers + h3 + heat siblings deployable
side-by-side via the layer contract.

## 1. Source description

Same Splunk Stream **TLS session** (`stream:tls`) sourcetype
as the companion [markers](./markers.md) and [heat](./heat.md)
recipes — passive wire-data capture from a SPAN / mirror /
cloud VPC mirror, indexed to the customer's wire-data index
(default `wire_data`).

**Why H3 hexbin for wire data.** A markers view at world
zoom collapses dense regional destination clusters (one CDN
edge fleet spans 200+ POPs worldwide; one cloud region
hosts hundreds of distinct endpoint IPs) into overlapping
circles. A heatmap (the [heat](./heat.md) recipe) smooths
that into a Gaussian pressure surface, which is great for
executive briefings — but for a NetOps panel where the
operator needs to **RANK regions and CLICK INTO them**,
the smooth heat gradient is the wrong shape. H3 hexbin
gives you regular hexagonal cells (Uber's
[H3 spatial index](https://h3geo.org/) — equal-area,
equal-shape, with predictable cell sizes per resolution
level) coloured by a deterministic per-cell aggregate
function (sum / max / avg of `bytes_out`), with each cell
behaving as a clickable drilldown affordance into the
contributing destinations.

**H3 hexbin vs heatmap vs markers — which to choose.**
- Use **markers** (per [splunk-stream/markers](./markers.md))
  when the panel question is "WHICH destination IPs should
  I investigate?" (SOC analyst investigation, IR triage,
  per-flow forensics).
- Use **heatmap** (per [splunk-stream/heat](./heat.md)) when
  the panel question is "WHERE is egress pressure SMOOTHLY
  DISTRIBUTED?" (executive data-residency briefing, multi-
  region availability slide, smooth gestalt).
- Use **H3 hexbin** (this recipe) when the panel question
  is "WHICH REGION is hottest, and can I CLICK INTO IT?"
  (NetOps capacity review, data-residency audit per
  geographic boundary, per-region rankings with drilldown).
- All three CAN coexist on the same Dashboard Studio panel
  via the BM-CT-1 layer contract. Recommended top-of-stack
  for splunk-stream: heat underneath (executive panel),
  hexbins overlay (NetOps drilldown), markers on top
  (per-IP SOC investigation) — three audiences, one panel.

**Typical sourcetype / index:** `sourcetype="stream:tls"` /
`index=wire_data` (per `splunk-stream-setup`'s default app
context).

## 2. SPL recipe

```spl
index=wire_data sourcetype="stream:tls"
| stats sum(bytes_out) AS bytes_out BY dest_ip
| iplocation dest_ip
| where isnotnull(lat) AND isnotnull(lon)
| where bytes_out >= 1048576
| eval value=bytes_out
| rename dest_ip AS id, Country AS dest_country
| fields id, lat, lon, dest_country, bytes_out, value
| sort - bytes_out
| head 10000
```

Why this exact shape, line by line:

- **`index=wire_data sourcetype="stream:tls"`** — base
  search. Same rationale as the markers and heat
  companions: TLS covers ~90 % of modern outbound flows
  and the SNI / dest_ip pair gives both application
  identity and the geo join key.
- **`stats sum(bytes_out) AS bytes_out BY dest_ip`** —
  collapse from per-session events to one row per
  destination IP, weighted by total outbound bytes. Same
  per-destination collapse as the heat recipe. The H3
  layer aggregates many destinations per cell using the
  `value` field; the per-destination row preserves
  enough cardinality for the per-cell `sum` to be
  meaningful (a cell with 50 destinations and 5 GB
  total is correctly "hotter" than a cell with 2
  destinations and 100 MB total).
- **`iplocation dest_ip`** — Splunk's built-in MaxMind
  GeoLite2 geocoder, server-side, no outbound network
  call. See the companion markers recipe for the MaxMind
  freshness discussion.
- **`where isnotnull(lat) AND isnotnull(lon)`** — drop
  destinations that don't geocode (RFC-1918, multicast,
  link-local). For a wire-data hexbin, dropping un-
  geocoded destinations is correct — they have no
  public-Earth position so they cannot land in any cell.
- **`where bytes_out >= 1048576`** — 1 MiB floor. Matches
  the heat recipe's filter (same rationale: the long-
  tail of TLS handshakes-only destinations would dilute
  per-cell aggregates without contributing meaningful
  byte volume). Tune by tenant: bandwidth-light SMB
  might drop the floor to 64 KiB; bulk-transfer-heavy
  SaaS might raise it to 64 MiB to focus only on
  significant egress destinations.
- **`eval value=bytes_out`** — **the H3 hexbin contract**.
  The layer expects a `value` field per row that it can
  aggregate across rows in the same cell (using whichever
  aggregate function the formatter's `hexbinAggregate`
  option picks). Setting `value` from `bytes_out` makes
  the hexbin colour represent "total / max / avg bytes
  out per region" depending on the §4 aggregate choice.
  To represent destination count instead of byte volume,
  set the aggregate to `count` and leave `value` as-is
  (the layer ignores `value` when aggregating by count).
- **`rename dest_ip AS id, Country AS dest_country`** —
  adopt Better Map's canonical `id` alias. `dest_country`
  flows through as a feature property for dashboard
  filtering ("show me only destinations in CN", "exclude
  US-domiciled traffic") — useful for data-residency
  audit panels.
- **`fields ...`** — explicit field list, six fields.
  Both `bytes_out` and `value` are carried even though
  they're numerically identical — `value` drives the
  hexbin aggregate, `bytes_out` is the human-readable
  field name surfaced in per-cell drilldown popups when
  paired with a companion markers overlay.
- **`sort - bytes_out`** — heaviest destinations first;
  combined with `head 10000` this gives the hexbin
  layer all the heavy egress destinations even when the
  long-tail is truncated. The hexbin layer aggregates
  many destinations per cell, so even 10000 destinations
  collapse to ~50-300 visible cells at typical world
  zoom + resolution 3.
- **`head 10000`** — render budget. Wire-data tenants
  carry thousands of distinct TLS destinations per 24 h
  above the 1 MiB threshold (typical tenant: 500-2000
  distinct heavy egress IPs per day — well under the
  cap; the cap is generous for bandwidth-heavy SaaS
  perimeters carrying 5000+ destinations).

Note every `|` starts its own physical line per the SPL
pipe-per-line contract.

## 4. Recommended formatter config

```json
{
  "pointRenderer": "h3",
  "hexbinAggregate": "sum",
  "hexbinResolution": 3,
  "hexbinOpacity": 0.7
}
```

Why this specific config:

- **`pointRenderer: "h3"`** — explicit pin to the H3
  hexbin renderer. The `auto` renderer never picks H3
  (it's a deliberate panel-design choice, not a fallback);
  must be set explicitly.
- **`hexbinAggregate: "sum"`** — **total bytes out per
  cell** is the natural aggregation for an egress-volume
  ranking panel. The cell colour reads as "the total
  egress bytes from all destinations in this hex" —
  exactly what a NetOps capacity-planning or data-
  residency-audit conversation wants ("our `us-east-1`
  hex received 5 TB of egress this week, vs the
  `eu-west-1` hex at 1.2 TB"). Different from the
  cim-performance/h3 recipe which uses `avg` (because
  averaging CPU% per cell is meaningful, but averaging
  byte-volume per cell would be diluted by the long
  tail of small destinations). For an "average egress
  per destination per cell" view (useful for "is this
  region typical or anomalous"), swap to `avg`. For
  "loudest destination per cell" (useful for outlier
  hunting), swap to `max`.
- **`hexbinResolution: 3`** — **resolution 3** = ~120 km
  edge length per cell. Per the
  [H3 resolution table](https://h3geo.org/docs/core-library/restable),
  resolution 3 cells comfortably contain entire metro
  areas (Greater London, Greater New York, Greater
  Tokyo) and are typically the right granularity for a
  world-zoom panel showing "egress per region". At
  resolution 3 the global hex count is ~41k — modest
  render load. For continent-zoom panels, raise to 4
  (~17 km cells, finer resolution within a continent).
  For per-country / data-residency-audit views, raise
  to 5 (~6 km cells — typically multiple cells per
  country, useful for "within country, where does the
  egress go"). For metro-zoom investigation, raise to
  6 (~2 km cells — each cloud region's data centers
  get distinct cells).
- **`hexbinOpacity: 0.7`** — matches every other H3 and
  heat recipe in the matrix (consistent visual style
  across layer types in mixed-layer dashboards). The
  H3 hexbin layer benefits slightly less from low
  opacity than the heat layer (hexes have sharp edges,
  so basemap city labels showing through a hex are less
  of an issue than showing through a Gaussian heat blob),
  but `0.7` keeps the panel visually consistent. Raise
  to `0.85-0.9` for an isolated H3-only panel where the
  basemap underlay matters less.
- **`value` is the H3-layer-required aggregation
  field.** Better Map's `dataFitness.js` auto-picks
  `value` by name. The SPL above already names the
  aggregation column `value`; no further formatter
  config needed. If you rename the column in SPL, set
  the formatter's `valueField` option (or whichever
  name the formatter schema uses — check
  [`docs/_machine/formatter-schema.json`](https://github.com/fenre/better_map/blob/main/docs/_machine/formatter-schema.json)).

## 6. Gotchas

- **H3 hexbin vs heatmap vs markers — when to choose
  which.** See the §1 source-description matrix. H3 is
  right for NetOps capacity reviews and data-residency
  audits (per-region rankings with clickable drilldown).
  Heat is right for executive briefings (smooth
  gradient reads cleaner in a slide deck). Markers
  are right for SOC analyst investigation (per-IP
  clickable detail). All three can coexist via the
  BM-CT-1 layer contract — heat underneath, hexbins
  overlay, markers on top. Toggle each independently
  from a dashboard input.
- **CDN destination smearing.** A single CDN provider
  (Cloudflare, Fastly, Akamai) operates POPs in 200+
  cities worldwide. Your egress to that CDN will land
  in WHICHEVER POP your nearest router sends you to —
  geographically dispersed across continents. The
  resulting hex cells correctly carry per-POP byte
  volumes, NOT concentrated at the CDN's HQ. This is
  the right answer for an egress-volume map ("we send
  5 TB/day to Cloudflare, distributed across 30
  cities — top cell is Cloudflare's San Francisco
  cluster at 600 GB/day") but is sometimes surprising
  to NetOps engineers who expect "all Cloudflare egress
  lights up at the Cloudflare HQ cell." If you need a
  CDN-grouped view, enrich `dest_ip` with an ASN
  lookup (`| iplocation dest_ip allfields=true`) and
  aggregate `BY as_name` BEFORE the geocoding step.
- **Aggregate function semantics.** `sum` (default)
  totals bytes per cell — the natural NetOps metric.
  `avg` averages bytes per destination per cell —
  useful for "is this region anomalous compared to
  baseline" but dilutes the heavy-hitter signal. `max`
  highlights the LOUDEST destination per cell — useful
  for outlier hunting and per-region top-talker
  identification. `count` reduces to destination
  density per cell — useful for "where are my
  destinations geographically distributed" (orthogonal
  question to byte volume; consider a separate panel
  with `count` for that view rather than overloading
  the byte-volume panel). Pick `sum` for capacity
  reviews and data-residency audits; `max` for outlier
  hunting; `avg` for anomaly baselining; `count` for
  distribution analysis (separate panel).
- **H3 cell SAMPLE SIZE matters less for wire data
  than for cim-performance.** A wire-data hex cell
  with 1 destination contributes that destination's
  full byte volume — meaningful at any resolution
  (because byte volume is additive). Compare to the
  cim-performance/h3 recipe where a single-host cell
  paints the whole region with that one host's CPU%
  — misleading. So this recipe does NOT need the
  per-cell sample-size filter that cim-performance/h3
  recommends in its Gotchas. The trade-off is that a
  cell with 1 destination and 1 destination with 5 TB
  reads identically to a cell with 50 destinations
  totalling 5 TB — by design, the heat blob represents
  AGGREGATE volume regardless of source diversity.
- **MaxMind GeoLite2 freshness.** Same as the companion
  markers and heat recipes. Splunk ships GeoLite2 but
  its refresh cadence is tied to the Splunk release
  train, not MaxMind's. If geo accuracy matters at the
  city level, refresh the database via `splunk cmd
  splunkd cmd geoip-update` or point `iplocation` at a
  fresher MaxMind / GeoIP2 file via `transforms.conf`
  `[geoip]` stanza. For country-level hexbins (i.e.
  data-residency audits at country granularity), the
  default freshness is fine — country boundaries don't
  move often. At resolution 5+ where individual cells
  resolve to sub-city granularity, freshness matters
  more.
- **`stream:tls` privacy / compliance.** Wire-data
  capture is a GDPR / HIPAA scope expander on most
  customers' compliance surface. The
  [`splunk-compliance` skill](https://github.com/fenre/better_map/blob/main/.cursor/rules/splunk-compliance.mdc)
  documents the controls. The H3 hexbin layer is BROADER
  than the markers layer (one cell covers many
  destinations) but NARROWER than the heat layer (sharp
  hexagonal boundaries vs smooth Gaussian blobs), so
  privacy-sensitive tenants should default to the
  hexbin or heat layer in audience-facing dashboards
  and reserve the markers layer for authenticated SOC
  workstations only.
- **Time range.** Hard-coded time range is the
  dashboard panel default — NOT a recipe-level
  constraint. Wire-data indexes are HIGH-volume; if
  you point the H3 hexbin at a 24 h window without
  index-level acceleration, the search-head CPU cost
  is substantial. The SPL above is search-time-friendly
  because `stats` happens before `iplocation` (the
  expensive geocoding only runs against pre-aggregated
  destinations), but the underlying raw-event scan is
  still O(events × seconds). Constrain the time range
  explicitly in the dashboard input AND consider
  summary-indexing the per-destination roll-up if the
  panel auto-refreshes more often than every 5 min.
- **No OT safety dependency, BUT.** Same as the
  companion markers and heat recipes — this recipe is
  IT-only by design. If your Stream forwarders are
  mirrored against an OT/ICS environment, the
  [`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
  Rules 1 + 2 apply: Stream IS the canonical passive
  collection method for OT (no active probes) but the
  resulting `dest_ip` set will contain Level-0/1/2 PLCs
  and HMIs. An H3 hexbin of those endpoints MUST NOT
  be wired to any SOAR / drilldown that could send a
  write back. Render-only is fine; render-and-act is
  not. Use the dedicated `cyber-vision` recipe wave
  for OT-aware wire-data presentation.

## Verification status

`status: unverified` in the frontmatter — the SPL is
structurally sound and follows the documented Splunk Stream
contracts plus the canonical `eval value=<metric>` H3 hexbin
aggregation pattern shared across every H3 recipe in the
matrix ([cim-alerts/h3](../cim-alerts/h3.md),
[cim-authentication/h3](../cim-authentication/h3.md),
[cim-network-traffic/h3](../cim-network-traffic/h3.md),

It has not been dispatched against a real `stream:tls` index
in the v1.7-prep development cycle (the lab tenant does not
have Splunk Stream forwarders deployed). A maintainer with a
Splunk tenant carrying Stream data should:

1. Confirm Stream data is flowing: `index=wire_data
   sourcetype="stream:tls" earliest=-1h | stats count`.
2. Run the recipe SPL and confirm the panel renders at
   least 10 distinct hex cells over a 24-hour window with
   all six documented fields populated for the non-RFC-1918
   destinations.
3. Run the markers and heat companions side by side and
   confirm the loudest hex cells correspond to the loudest
   markers AND to the brightest heat blobs (sanity check
   on the per-cell `sum` aggregation).
4. Verify per-cell drilldown works: click into a hex to
   see the list of contributing destinations with
   `bytes_out` values.
5. Tune `hexbinResolution` to match the panel's zoom level
   (3 for world, 4 for continent, 5 for state/country, 6
   for metro).
6. Update the frontmatter to `status: verified`, fill in
   `verified_against` (e.g. "Splunk Enterprise 10.0 with
   Splunk_TA_stream 9.0.1 against a 5-host SPAN aggregate"),
   and submit a follow-up PR. The CI gate
   `scripts/check-recipe-schema.py` will accept the change
   without touching the schema.

The D5 Phase 1 harness (`docker/`) makes this a 2-minute
round-trip once an operator has Stream data to point it at
— see the
[local Splunk harness operator guide](https://github.com/fenre/better_map/blob/main/docs/development/local-splunk-harness.md).
