# CIM Alerts — H3 hexbin

The geographic-aggregation complement to the
[cim-alerts/markers](./markers.md) recipe — same CIM-
accelerated `Alerts` data model, same `iplocation`
geocoding of `dest` (the host firing the alert), but
rendered as H3 hexagonal cells coloured by aggregate
alert-count rather than discrete per-host markers. The
H3 layer surfaces **per-region alert PRESSURE** as hex
cell colour intensity: hot hexes indicate regions
hosting the noisiest hosts; cool hexes indicate quiet
regions. The natural shape when the SOC stand-up
question is "which geographic CELL is hottest right
now and how do we rank cells against each other?"
rather than "show me each noisy host" (markers
companion).

## 1. Source description

Same Splunk **Alerts** Common Information Model (CIM)
data model as the [cim-alerts/markers](./markers.md)
companion — vendor-agnostic because the data model
normalises every event tagged `alert` regardless of
producer (ES correlation searches, ITSI notable
events, Mission Control episodes, third-party SIEM
forwarders, IDS / IPS / EDR appliances). See the
markers companion for the full list of contributing
sourcetypes.

**Why H3 hexbin for CIM Alerts.** The markers view is
the right shape for SOC analyst investigation ("which
specific host fired 47 alerts and what were they?")
but it's the wrong shape for SOC leadership
situational awareness ("which datacenter / metro /
region is producing the most noise right now?"). H3
hexbin renders each region as a discrete clickable
hexagon with a deterministic per-cell aggregate (the
sum of alert counts across all destination hosts
inside the cell), so the operator can rank regions
visually and click any hot hex to see the
contributing hosts in a drilldown panel. The right
layer for **SOC daily-stand-up dashboards** and
**executive-briefing slide decks** where the
audience needs regional pressure ranking, NOT for
per-host investigation (markers) and not for the
acceleration-incompatible heatmap pattern (the heat
layer wants a `weight` field that doesn't naturally
fall out of the CIM Alerts aggregation contract —
the h3 layer's `value` aggregate is the better
shape).

**markers vs H3 hexbin — when to choose which.**

- Use **markers** when the question is "show me each
  noisy host individually" (SOC analyst triage, IR
  drilldown). Per
  [cim-alerts/markers](./markers.md).
- Use **H3 hexbin** when the question is "which
  REGIONS are hottest and let me drill into the
  leader" (SOC daily stand-up, NOC overview,
  executive briefing). This recipe.

Both layers can coexist on the same dashboard via the
BM-CT-1 layer contract — operators toggle between
regional and per-host views without re-running the
underlying search.

**Typical sourcetype / index:** anything tagged
`alert` (check `| tstats values(sourcetype) WHERE
\`cim_Alerts_indexes\` tag=alert`); typical indexes
are `notable` (ES correlation results),
`itsi_tracked_alerts` (ITSI), `summary` (saved-search
aggregation), and the SIEM-forwarder indexes
(`pan_logs`, `crowdstrike`, etc.). This recipe queries
the data-model accelerated summary, so the source
index does not appear in the SPL.

## 2. SPL recipe

```spl
| tstats summariesonly=true count AS alert_count, dc(Alerts.signature) AS distinct_signatures, values(Alerts.severity) AS severities FROM datamodel=Alerts WHERE earliest=-24h BY Alerts.dest
| rename "Alerts.dest" AS dest
| iplocation dest
| where isnotnull(lat) AND isnotnull(lon)
| where alert_count >= 1
| eval max_severity=case(mvfind(severities, "^critical$") >= 0, "critical", mvfind(severities, "^high$") >= 0, "high", mvfind(severities, "^medium$") >= 0, "medium", mvfind(severities, "^low$") >= 0, "low", mvfind(severities, "^informational$") >= 0, "informational", true(), "unknown")
| eval value=alert_count
| rename dest AS id
| fields id, lat, lon, value, max_severity, distinct_signatures
| sort - value
| head 10000
```

Why this exact shape, line by line:

- **`| tstats summariesonly=true count AS alert_count,
  dc(Alerts.signature) AS distinct_signatures,
  values(Alerts.severity) AS severities FROM
  datamodel=Alerts`** — reads the CIM-accelerated
  Alerts data model summary. Three aggregates per
  destination: the alert count (drives hex cell
  colour intensity), the distinct signature count
  (drives the popup story — one host firing 47
  alerts of ONE signature is a noisy correlation
  rule; 47 alerts of 8 signatures is a real
  multi-pronged event), and the severity multi-value
  set (folded down to `max_severity` for popup
  display).
- **`WHERE earliest=-24h`** — bind the alert pressure
  to a 24 h window. Matches the markers companion
  and the typical SOC stand-up cadence.
- **`BY Alerts.dest`** — one row per unique
  destination host. The hex layer then SUMS the
  `value` (alert_count) per host across all hosts
  inside a cell, giving a per-cell total-alert-count
  colour. One hot hex over Seattle might be ONE
  host with 1000 alerts OR 100 hosts with 10 alerts
  each; the popup's `distinct_signatures` aggregate
  helps disambiguate.
- **`| iplocation dest`** — Splunk's built-in MaxMind
  GeoLite2 geocoder. Same caveat as the markers
  companion: hostname `dest` values (internal
  hostnames without DNS suffix) silently fail to
  geocode and get filtered. For internal-host
  visibility, swap `iplocation` for a `lookup
  host_geocoded.csv` join on a customer-curated
  asset CMDB.
- **`| where isnotnull(lat) AND isnotnull(lon)`** —
  drop RFC-1918 internal sources so they don't pile
  up at Null Island. Same defensive filter as the
  cim-authentication/h3 sibling.
- **`| where alert_count >= 1`** — defensive guard
  (the `tstats count` aggregation guarantees this is
  always true post-aggregation, but the line makes
  the intent explicit and survives any future
  rewrite that introduces a fillnull). NOT a
  noise-floor filter — for that, raise the threshold
  to `>= 5` or higher per the tenant's baseline
  alert rate.
- **`| eval max_severity=case(...)`** — same severity
  folding as the markers companion. Surfaces in the
  popup so the operator can distinguish a hot hex
  full of `informational` alerts from a hot hex with
  one `critical` mixed in.
- **`| eval value=alert_count`** — **the H3 hexbin
  contract**. The layer expects a `value` field per
  row that it can aggregate across rows in the same
  cell (using whichever aggregate function the
  formatter's `hexbinAggregate` option picks).
  Setting `value` from alert_count makes the hex
  colour represent "total alerts attributed to this
  region" (per the §4 formatter config).
- **`| rename dest AS id`** — adopt Better Map's
  canonical `id` alias. Different from the markers
  companion (which compounds dest + timestamp to
  prevent dedup across snapshots) because the H3
  layer aggregates across rows by lat/lon
  bucketing, not by id — collisions on `id` are
  benign for hexbin.
- **`| head 10000`** — render budget. The H3 hexbin
  layer collapses 10000 destination hosts into at
  most a few hundred visible hex cells at resolution
  3, so the panel stays responsive even on the
  busiest ES installs (typical ES tenants generate
  10k-100k alerts/day across thousands of unique
  hosts).

Every `|` starts its own physical line per the SPL
pipe-per-line contract in `splunk-conf-and-spl.mdc`.

## 4. Recommended formatter config

```json
{
  "pointRenderer": "h3",
  "hexbinAggregate": "sum",
  "hexbinResolution": 3,
  "hexbinOpacity": 0.7
}
```

Why this specific config:

- **`pointRenderer: "h3"`** — explicit pin to the H3
  hexbin renderer. The `auto` renderer never picks
  H3 (it's a deliberate panel-design choice, not a
  fallback); must be set explicitly.
- **`hexbinAggregate: "sum"`** — **sum the alert
  counts per cell**. The cell colour reads as "the
  total alerts attributed to this region in the
  last 24 h" — exactly the question the SOC daily
  stand-up needs answered. Other valid aggregates
  per the
  [formatter schema](https://github.com/fenre/better_map/blob/main/docs/_machine/formatter-schema.json):
  `max` (worst single host per cell — useful for
  "which cell has the loudest single offender?"),
  `avg` (average alert count per host per cell —
  useful for "is this a fleet-wide noisy region or
  a single-host outlier?"), `count` (host density
  per cell — but if that's the question, the
  cim-authentication/heat pattern with a weight
  aggregation is the better choice once acceleration
  shapes are sorted).
- **`hexbinResolution: 3`** — **resolution 3** =
  ~120 km edge length per cell. Same default as
  the cim-authentication/h3 sibling. Per the
  [H3 resolution table](https://h3geo.org/docs/core-library/restable),
  resolution 3 cells comfortably contain entire
  metro areas and are typically the right
  granularity for a world-zoom panel showing
  "alert pressure per region." For continent-zoom
  panels, raise to 4 (~17 km cells); for
  per-country views, raise to 5 (~6 km cells).
  Lower resolutions (1, 2) produce 1-3 ENORMOUS
  hexes per country that read as country-level
  chunks rather than regional pressure —
  generally too coarse for actionable drilldown.
- **`hexbinOpacity: 0.7`** — same opacity as the
  cim-authentication/h3 and cim-performance/h3
  siblings. Visually consistent across layer
  types in mixed-layer dashboards.
- **`value` is the H3-layer-required aggregation
  field.** Better Map's `dataFitness.js`
  auto-picks `value` by name (same convention as
  `weight` for heatmap, `bytes_out` for
  choropleth). The SPL above already names the
  aggregation column `value`; no further
  formatter config needed.

## 6. Gotchas

- **CIM data-model acceleration MUST be enabled.**
  Same as the markers companion — if the Alerts data
  model is not accelerated, the `tstats
  summariesonly=true` query returns zero rows.
  Confirm in Settings → Data models → Alerts →
  Acceleration. The alternative `summariesonly=false`
  works but scans raw events — minutes to hours on
  busy ES installs.
- **markers vs H3 hexbin — when to choose which.**
  See §1 above. The H3 hexbin's distinguishing
  advantage is regional ranking — operators can
  visually rank cells by colour intensity. Markers
  drilldown to ONE host per click; H3 cells
  drilldown to a LIST of hosts per cell.
- **H3 cell SAMPLE SIZE matters.** A hex cell with
  ONE host inside it shows that one host's
  alert_count as the cell's total — misleading at
  world zoom (one extreme outlier in a sparse
  region paints a whole cell red and obscures the
  regional comparison the panel is supposed to
  surface). Add a `where source_ip_count >= 3`
  filter (after a pre-aggregation by H3 index) if
  your tenant has sparse regions. Pattern matches
  the cim-authentication/h3 sibling.
- **Aggregate function semantics.** `sum` totals
  alert counts across the cell — sensitive to one
  loud host. `max` highlights the worst host per
  cell — clearer signal for incident detection but
  loses the "is this a fleet-wide noisy region or a
  single-host outlier" distinction. `avg` produces
  "average alerts per host per cell" — meaningful
  for comparing alert intensity vs alert breadth
  across cells. Pick `sum` for SOC-stand-up
  totals; `max` for incident war rooms; `avg` for
  comparative intensity panels.
- **`Alerts.dest` is sometimes a hostname, sometimes
  an IP.** Same caveat as the markers companion.
  `iplocation` only geocodes IPs. For hostname
  `dest` values, rows render with null lat/lon and
  get filtered out by the `where isnotnull` clause
  — they silently disappear from the hex grid. For
  customers with a populated internal asset CMDB,
  replace the `iplocation` stage with a lookup join
  against a `host_geocoded.csv` lookup.
- **Severity nomenclature is vendor-specific.** Same
  caveat as the markers companion — some vendors
  emit `severity="3"` (integer), some
  `severity="HIGH"` (uppercase). The `case(...)`
  uses lowercase ordering — defensive against the
  typical `Splunk_SA_CIM` field-alias chain that
  normalizes to lowercase. If your data is escaping
  that normalization, add a `| eval
  severities=mvmap(severities, lower(x))` line
  before the `eval max_severity=case(...)`.
- **`alert_count` units depend on what generated the
  alerts.** Same as the markers companion. An ES
  correlation search firing once per matched event
  produces a different count semantic from an ITSI
  episode that groups N notable events. The hex
  cell aggregate sums them all the same way — at
  the regional-pressure level this is the right
  semantic (region X has more total alerts than
  region Y, regardless of how each was grouped),
  but be aware when drilling into a single cell
  that the per-host counts may be heterogeneous.
- **Time range.** The recipe hard-codes
  `earliest=-24h`. Replace with
  `earliest=$earliest$` once you wire the recipe
  into a dashboard with a time-range input. For
  SOC stand-up panels a fixed 24 h window matches
  the shift change; for longer-horizon trend
  panels, raise to `-7d` and consider raising the
  `head 10000` cap to `100000` to absorb the wider
  destination set.
- **PII / GDPR posture.** `dest` is a hostname or
  IP — pseudonymous in most tenants. The H3 hexbin
  panel is generally LOWER-risk than the markers
  companion for privacy-sensitive deployments
  because the cell aggregate collapses individual
  hosts into a regional count, but the popup may
  still expose hostname-level data when the
  operator drills into a cell. Per ROADMAP §1a
  (binding), Better Map NEVER sends event data
  outside `splunkd:8089`. `iplocation` runs
  server-side against the local MaxMind database.
- **No OT safety dependency.** The Alerts data
  model is a general-purpose alert aggregator. If
  your ES correlation searches include
  OT-related signals (e.g., Cyber Vision IDS
  alerts on a Level-2 historian, ITSI episodes
  triggered by Edge Hub anomalies), the alerts
  ARE emitted from OT-adjacent detection, but the
  recipe never reads from a Level-0/1/2 source
  directly — the alert (a Level-3 or Level-4
  artefact produced by the SIEM / ITSI / EDR
  engine) is the input. Per
  [`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
  Rule 6, any OT-safety-dependent detection should
  carry `safety_dependent: true` metadata in the
  correlation search / ITSI policy AND its
  runbook should include an OT-engineering
  escalation step — those are upstream contracts
  of the alert authoring, not this recipe.

## Verification status

`status: unverified` in the frontmatter — the SPL is
structurally sound, follows the documented Splunk
CIM Alerts contract plus the canonical `tstats count
BY ... | eval value=count` H3 aggregation pattern
(matches the cim-authentication/h3 +
cim-performance/h3 + cim-network-traffic/h3 +
meraki/h3 + csv-lookup-geo/h3 +
netflow-sflow-ipfix/h3 + es-risk/h3 recipes), and
uses only shipping Splunk built-ins (`tstats`,
`iplocation`, `case`, `mvfind`). It has not been
dispatched against the v1.7-prep lab tenant in this
PR because (a) non-interactive admin auth is not
present in the agent workspace, and (b) the
v1.7-prep lab does not carry a populated CIM Alerts
data model (no ES install, no correlation
searches). A maintainer with REST auth to an
ES-enabled tenant should:

1. Run the recipe SPL with `summariesonly=false`
   first to confirm the Alerts data model has data
   for the queried time range and `dest` is
   populated.
2. Re-run with `summariesonly=true` (the recipe
   shape) to confirm acceleration is alive and
   returns the same shape.
3. Tune the `head 10000` cap for the tenant's
   alert breadth (see Gotchas).
4. Render the panel at resolutions 3, 4, 5 to
   confirm the hex grain matches the dashboard
   zoom.
5. Run the markers companion side by side and
   confirm the hottest hex cells correspond to
   the most-noisy markers (sanity check on the
   `value` aggregation and the `head 10000`
   truncation).
6. Update the frontmatter to `status: verified`,
   fill in `verified_against`, and submit a
   follow-up PR.
