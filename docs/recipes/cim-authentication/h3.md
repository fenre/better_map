# CIM Authentication — H3 hexbin

The geographic-aggregation complement to the
[cim-authentication/markers](./markers.md) and
[cim-authentication/heat](./heat.md) recipes — same CIM-
accelerated `Authentication` data model, same `iplocation`
geocoding of failed-login source IPs, but rendered as H3
hexagonal cells coloured by aggregate failure-count rather
than discrete markers or smooth heat blobs. The H3 layer
surfaces **per-region failed-authentication PRESSURE** as
hex cell colour intensity: hot hexes indicate metro areas /
countries producing the most failed attempts; cool hexes
indicate quiet regions. This is the natural shape when the
dashboard question is "which geographic CELL is hottest
and how do we rank cells against each other?" rather than
"show me each attacker" (markers) or "show me a smooth
pressure gradient" (heatmap).

## 1. Source description

Same Splunk **Authentication** Common Information Model
(CIM) data model as the companion [markers](./markers.md) /
[heat](./heat.md) recipes — vendor-agnostic because the
data model normalises Active Directory, Entra ID / M365,
Okta, AWS CloudTrail, Cisco Duo, Cisco ISE, Linux PAM,
Workday, Salesforce, GitHub Enterprise, and every other
authentication source tagged `tag=authentication`.

**Why H3 hexbin for CIM Authentication.** A heatmap view
of identity attack pressure is excellent for executive
briefings (smooth gradient reads cleanly in a slide deck)
but it's not the right layer when the operator needs to
DRILL INTO a region ("which AS / city is contributing the
417 failures in that Amsterdam blob?"). H3 hexbin renders
each region as a discrete clickable hexagon with a
deterministic per-cell aggregate (the sum of failure
counts across all source IPs inside the cell), so the
operator can click any hot hex to see the contributing
source IPs in a drilldown panel. The right layer for
**SOC daily-stand-up dashboards** where the operator
wants to rank regions and drill into the leader,
NOT for per-IP investigation (markers) and not for
smooth pressure gradients (heatmap).

**Heatmap vs H3 hexbin vs markers — when to choose which.**
- Use **markers** when the question is "show me each
  attacker individually" (SOC analyst investigation, IR
  triage). Per [cim-authentication/markers](./markers.md).
- Use **heatmap** when the question is "show me attack
  pressure as a smooth gradient" (executive briefing,
  SOC leadership slide deck). Per
  [cim-authentication/heat](./heat.md).
- Use **H3 hexbin** when the question is "which REGIONS
  are hottest and let me drill into the leader" (SOC
  daily stand-up, threat-region-of-the-day briefing,
  RIR-precursor visibility). This recipe.

**Typical sourcetype / index:** anything tagged
`authentication` (check `| tstats values(sourcetype) WHERE
\`cim_Authentication_indexes\` tag=authentication`); typical
index is `authentication`, `wineventlog`, `okta`, `o365`, or
the vendor-specific index. This recipe queries the data-
model accelerated summary, so the source index does not
appear in the SPL.

## 2. SPL recipe

```spl
| tstats summariesonly=true count AS failure_count, dc(Authentication.user) AS distinct_users FROM datamodel=Authentication WHERE Authentication.action="failure" earliest=-24h latest=now BY Authentication.src
| rename Authentication.src AS src
| where match(src, "^\d+\.\d+\.\d+\.\d+$")
| iplocation src
| where isnotnull(lat) AND isnotnull(lon)
| where failure_count >= 5
| eval value=failure_count
| rename src AS id, Country AS src_country
| fields id, lat, lon, value, src_country, distinct_users
| sort - value
| head 10000
```

Why this exact shape, line by line:

- **`| tstats summariesonly=true count AS failure_count,
  dc(Authentication.user) AS distinct_users FROM
  datamodel=Authentication`** — reads the CIM-accelerated
  Authentication data model summary. Two aggregates per
  source IP: the failure count (drives hex cell colour
  intensity) and the distinct user count (drives the
  popup story — a single source IP failing against many
  users is password spray; a single source IP failing
  against ONE user is brute force). Both surface in the
  popup when the operator drills into a hex cell.
- **`WHERE Authentication.action="failure"`** — filter
  at the data-model layer. Change to `"success"` to flip
  the panel to a "where are successful logins coming
  from regionally?" posture-monitoring view.
- **`BY Authentication.src`** — one row per unique source
  IP. The hex layer then SUMS the `value` (failure_count)
  per source IP across all source IPs inside a cell,
  giving a per-cell total-failure-count colour. One hot
  hex over Amsterdam might be ONE source IP with 10000
  failures OR 100 source IPs with 100 failures each;
  the popup's `distinct_users` aggregate helps
  disambiguate.
- **`| where match(src, "^\d+\.\d+\.\d+\.\d+$")`** — IPv4-
  only filter. Drop or relax for IPv6-heavy environments.
- **`| iplocation src`** — Splunk's built-in MaxMind
  GeoLite2 geocoder. No outbound network call.
- **`| where isnotnull(lat) AND isnotnull(lon)`** — drop
  RFC-1918 internal sources (legitimate ops staff fat-
  fingering passwords) so they do not pile up at Null
  Island and visually dominate the panel.
- **`| where failure_count >= 5`** — signal-to-noise
  filter, same as the markers / heat companions. Tune
  to your tenant's baseline failure noise floor.
- **`| eval value=failure_count`** — **the H3 hexbin
  contract**. The layer expects a `value` field per row
  that it can aggregate across rows in the same cell
  (using whichever aggregate function the formatter's
  `hexbinAggregate` option picks). Setting `value` from
  failure_count makes the hex colour represent "total
  failed-authentication attempts attributed to this
  region" (per the §4 formatter config).
- **`| rename src AS id, Country AS src_country`** —
  adopt Better Map's canonical `id` alias. `src_country`
  flows through as a feature property for the per-cell
  popup (the cell shows the dominant country of the
  contributing source IPs).
- **`| head 10000`** — render budget. The H3 hexbin layer
  collapses 10000 source IPs into at most a few hundred
  visible hex cells at resolution 3, so the panel stays
  responsive even on the noisiest tenants.

## 4. Recommended formatter config

```json
{
  "pointRenderer": "h3",
  "hexbinAggregate": "sum",
  "hexbinResolution": 3,
  "hexbinOpacity": 0.7
}
```

Why this specific config:

- **`pointRenderer: "h3"`** — explicit pin to the H3
  hexbin renderer. The `auto` renderer never picks H3
  (it's a deliberate panel-design choice, not a
  fallback); must be set explicitly.
- **`hexbinAggregate: "sum"`** — **sum the failure
  counts per cell**. The cell colour reads as "the
  total failed-authentication attempts attributed to
  this region in the last 24 h" — exactly the question
  the SOC daily stand-up needs answered. Other valid
  aggregates per
  [`docs/_machine/formatter-schema.json`](https://github.com/fenre/better_map/blob/main/docs/_machine/formatter-schema.json):
  `max` (worst single source IP per cell — useful for
  "where is the loudest attacker geographically?"),
  `avg` (average failure count per source IP per cell —
  useful for "where are the most determined attackers?"),
  `count` (just source-IP density — but if that's the
  question, use the cim-authentication/heat companion
  with the weight aggregation instead).
- **`hexbinResolution: 3`** — **resolution 3** = ~120 km
  edge length per cell. Per the
  [H3 resolution table](https://h3geo.org/docs/core-library/restable),
  resolution 3 cells comfortably contain entire metro
  areas (Greater London, Greater New York, Greater
  Amsterdam) and are typically the right granularity
  for a world-zoom panel showing "identity attack
  pressure per region." At resolution 3 the global hex
  count is ~41k — modest render load. For continent-
  zoom panels (e.g. "show me only European identity
  pressure"), raise to 4 (~17 km cells, finer
  resolution within a continent). For per-country
  views, raise to 5 (~6 km cells). Lower resolutions
  (1, 2) produce 1-3 ENORMOUS hexes per country that
  read as country-level chunks rather than regional
  pressure — generally too coarse for actionable
  drilldown.
- **`hexbinOpacity: 0.7`** — same opacity as the
  cim-performance/h3 recipe. The H3 hexbin layer
  benefits slightly less from low opacity than the
  heat layer because hexes have sharp edges (basemap
  city labels showing THROUGH a hex are less of an
  issue than showing through a Gaussian heat blob),
  but `0.7` keeps the panel visually consistent across
  layer types in mixed-layer dashboards. Raise to
  `0.85-0.9` for an isolated H3-only panel where the
  basemap underlay matters less.
- **`value` is the H3-layer-required aggregation
  field.** Better Map's `dataFitness.js` auto-picks
  `value` by name (per the same convention as `weight`
  for heatmap, `bytes_out` for choropleth, etc.). The
  SPL above already names the aggregation column
  `value`; no further formatter config needed.

## 6. Gotchas

- **CIM data-model acceleration MUST be enabled.** Same
  as the markers / heat companions — if the
  Authentication data model is not accelerated, the
  `tstats summariesonly=true` query returns zero rows.
  Confirm in Settings → Data models → Authentication →
  Acceleration.
- **H3 hexbin vs heatmap vs markers — when to choose
  which.** See §1 above. H3 hexbin's distinguishing
  advantage is per-cell drilldown — click a hex to see
  the list of contributing source IPs in a companion
  table panel. Heatmap has no clickable cells; markers
  drilldown to ONE source IP per click. For "show me
  the top 3 attack regions and let me drill into them,"
  H3 is the right layer; for "show me attack pressure
  smoothly," heatmap; for "show me each attacker,"
  markers. All three can coexist via the BM-CT-1 layer
  contract.
- **H3 cell SAMPLE SIZE matters.** A hex cell with ONE
  source IP inside it shows that one IP's failure
  count as the cell's total — misleading at world zoom
  (one extreme outlier in a sparse region paints a
  whole cell red and obscures the regional comparison
  the panel is supposed to surface). Add a `where`
  filter to drop cells with insufficient source-IP
  count if your tenant has sparse regions. The H3
  layer does not currently expose a per-cell-count
  threshold formatter option; the easiest workaround
  is a SPL pre-aggregation:
  `| stats sum(failure_count) AS cell_total, dc(id) AS
  source_ip_count BY <h3_index>` then
  `| where source_ip_count >= 3` before the panel
  visualisation. This requires the `splunkbase:h3` app
  for the per-cell H3 index function.
- **Aggregate function semantics.** `sum` totals
  failure counts across the cell — sensitive to one
  loud source IP. `max` highlights the worst source IP
  per cell — clearer signal for incident detection but
  loses the "is this a fleet attack or a single-IP
  attack" distinction. `avg` produces "average
  failures per source IP per cell" — meaningful for
  comparing attack intensity vs attack breadth across
  cells. `count` reduces to source-IP density which
  the heat companion already shows with a smoother
  gradient. Pick `sum` for SOC-stand-up totals; `max`
  for incident war rooms; `avg` for attacker-intensity
  comparisons.
- **`tag=authentication` membership.** If your IdP /
  VPN events are NOT being tagged for the data model
  (a common Splunk Cloud finding — bring-your-own-app
  pipelines often skip `eventtypes.conf` and
  `tags.conf`), they will be invisible to this recipe.
  Check `| tstats count WHERE
  \`cim_Authentication_indexes\` tag=authentication BY
  sourcetype`. Any sourcetype you EXPECT to see that
  does NOT appear is a CIM-compliance gap — fix the
  TA / `eventtypes.conf` and re-run.
- **`failure_count >= 5` threshold is workload-
  dependent.** Same advice as the markers / heat
  companions: tune so the hex ramp is dominated by
  ATTACKERS, not by Monday-morning Active-Directory
  password-reset traffic. For more sophisticated
  noise-filtering, see the RBA skill
  ([`~/.cursor/skills/splunk-rba/SKILL.md`](https://github.com/fenre/better_map/blob/main/.cursor/rules/splunk-rba.mdc)).
- **MaxMind database licensing.** Splunk Enterprise
  ships with the free MaxMind GeoLite2 database. For
  higher accuracy / commercial use, swap in MaxMind
  GeoIP2 via the Splunk admin UI. The recipe is
  unchanged.
- **Time range.** The recipe hard-codes `earliest=-24h
  latest=now`. Replace with `earliest=$earliest$
  latest=$latest$` once you wire the recipe into a
  dashboard with a time-range input. For SOC stand-up
  panels a fixed 24 h window is common (matches the
  shift change); for longer-horizon trend panels, raise
  to `-7d` and consider raising `failure_count >= 5`
  to `>= 25` to keep the cell-aggregate stable across
  the wider window.
- **VPN / proxy egress IPs distort the picture.** Same
  as the markers / heat companions — a heavy enterprise
  VPN concentrator emits failures from a single publish
  IP, and one such IP inside a hex cell can dominate
  the cell's aggregate. Add `NOT src IN
  ("198.51.100.0/24")` or join against a known-good
  corporate IP allow-list before rendering.
- **PII / GDPR posture.** Per ROADMAP §1a (binding),
  Better Map NEVER sends event data outside
  `splunkd:8089`. `iplocation` runs server-side against
  the local MaxMind database — no outbound geocoding
  API call. `src` IPs are pseudonymous; the H3 hexbin
  panel is generally LOWER-risk than the markers
  companion for privacy-sensitive deployments because
  the cell aggregate collapses individual source IPs
  into a regional count, but the popup may still
  expose source-IP-level data when the operator drills
  into a cell. Do NOT join against `identities.csv`
  (the ES Asset & Identity framework lookup) in this
  recipe — the username column would land in a public-
  facing dashboard and surface PII.
- **No OT safety dependency.** This recipe is pure IT
  identity-and-access. If your tenant ALSO logs OT
  operator console logins (RSLogix, FactoryTalk View,
  Wonderware InTouch, Siemens TIA Portal) under the
  Authentication data model, filter THOSE sourcetypes
  out of THIS panel (`NOT sourcetype IN
  ("rslogix:audit", "factorytalk:*")`) and put them in
  a DEDICATED recipe with explicit OT-safety
  annotations per
  [`/.cursor/rules/ot-safety.mdc`](https://github.com/fenre/better_map/blob/main/.cursor/rules/ot-safety.mdc)
  Rule 6 — a failed login to an HMI on a SIS bypass is
  a safety-relevant signal, NOT an IT credential-abuse
  signal, and rendering it as a low-priority hex
  alongside botnet pressure from Eastern Europe is
  exactly the kind of categorisation error Rule 6 is
  designed to prevent.

## Verification status

`status: unverified` in the frontmatter — the SPL is
structurally sound, follows the documented Splunk CIM
Authentication contract plus the canonical
`tstats count BY ... | eval value=count` H3 aggregation
pattern (matches the cim-performance/h3 +
cim-network-traffic/h3 + meraki/h3 + csv-lookup-geo/h3 +
netflow-sflow-ipfix/h3 recipes), and uses only shipping
Splunk built-ins (`tstats`, `iplocation`,
`Splunk_SA_CIM`). It has not been dispatched against the
v1.7-prep lab tenant in this PR because non-interactive
admin auth is not present in the agent workspace. A
maintainer with REST auth to a CIM-accelerated tenant
should:

1. Run the recipe SPL with `summariesonly=false` first
   to confirm the Authentication data model has data
   for the queried time range and `action="failure"` is
   populated.
2. Re-run with `summariesonly=true` (the recipe shape)
   to confirm acceleration is alive and returns the
   same shape.
3. Tune `failure_count >= 5` for the tenant's baseline
   noise floor (see Gotchas).
4. Render the panel at resolutions 3, 4, 5 to confirm
   the hex grain matches the dashboard zoom.
5. Run the markers and heat companions side by side
   and confirm the hottest hex cells correspond to
   the loudest markers / hottest heat blobs (sanity
   check on the `value` aggregation and the `head
   10000` truncation).
6. Update the frontmatter to `status: verified`, fill
   in `verified_against`, and submit a follow-up PR.
